========================================
Realtek RTL9602C and the ODI DFP-34X-2C3
========================================

Overview
========

The Realtek RTL9602C is a system-on-chip for GPON optical network units (ONUs).
Its processor is one Lexra LX5281 core, a big-endian MIPS I design that Linux
runs as an R3000-class CPU. Around the core the chip has a peripheral window
(system controller, console UART, interrupt controller, general-purpose timers,
watchdog and GPIO bank), an Ethernet switch with a DMA engine on its CPU port
and, behind the switch's PON port, the GPON MAC and the PON MAC.

The ODI DFP-34X-2C3 is a GPON ONU in an SFP module built on this SoC, with 32
MiB of DRAM and 8 MiB of SPI NOR flash. Its only electrical data interface is
the SFP edge connector, wired to the switch's SerDes lane; the GPON MAC drives a
separate laser driver IC that the SoC reaches over I2C.

This page is the reference for the MIPS side of the port: the CPU core, the
memory map, the platform code, the watchdog, the GPIO bank, the flash and its
partitions, the board's device tree and the contract under which the boot loader
starts the kernel. The switch, the CPU port's DMA engine, the GPON and PON MACs
and the optics have their own drivers under ``drivers/net/`` and are described
with them.

Configuration
-------------

``CONFIG_RTL9602C`` (``arch/mips/Kconfig``, "Realtek RTL9602C (Lexra LX5281)
based machines") is a member of the MIPS system-type choice. It builds
``arch/mips/rtl9602c/``, selects the CPU, cache, interrupt, console,
image-format and device-tree options that the core and the boot loader need
(listed under "Build and configuration") and is what ``GPIO_REALTEK_OTTO`` and
``RTL9602C_ETH`` depend on. ``rtl9602c_defconfig`` (``arch/mips/configs/``) is
the configuration of the board. The settings of it that this page relies on:

Interfaces to user space
------------------------

- ``/proc/cpuinfo``: ``system type`` reads ``Realtek RTL9602C`` and
  ``cpu model`` names ``Lexra LX5281``.
- ``/proc/cmdline`` and the ``Kernel command line:`` line of the kernel log:
  ``panic=10`` from the tree, then the boot loader's arguments.
- ``/proc/interrupts``: the SoC's interrupt sources appear under
  ``rtl9602c-intc``, the tick as ``timer@18003200`` and the console as
  ``ttyS0``.
- ``/dev/ttyS0``: the console, at 115200 baud.
- ``/dev/watchdog`` (and the watchdog core's sysfs entries): a watchdog the
  boot loader armed is fed by the kernel until the device is opened, for 60 s
  at most; procd opens it and feeds it.
- ``/sys/class/mtd/mtd0`` to ``mtd7`` and the block devices 31:0 to 31:7: the
  flash partitions, the boot loader's read-only and the others writable (see
  "Flash and partitions").
- A gpiolib chip of 32 lines; line 13 is requested by the switch driver as
  TX_DISABLE.
- ``reboot``, ``halt`` and ``poweroff``: reboot resets the whole chip through the
  watchdog driver's restart handler; halt and power off spin with interrupts
  disabled.

How to read the fact tables
===========================

Each block below has a short account of what the hardware does and what the code
does with it, followed by fact tables with three columns: *Fact*, *Tag* and
*Checked by*. The tag says how the fact is established. **M**, measured on the
board: *Checked by* gives the command or observation, through the driver's own
interfaces (the kernel log, ``/proc``, sysfs, debugfs, ``devlink``,
``ethtool``), that shows it. **T**, tested by function: the driver depends on
the fact, and the named behaviour fails if it is wrong. **P**, public standard:
*Checked by* names the document and the clause. **I**, inferred, not verified:
the fact is an assumption, and *Checked by* says what would confirm or refute
it. The last chapter collects these facts and says which of them the driver
depends on.

A row with two tags is established in two ways, or in two parts; *Checked by*
says which part carries which tag. "Every boot" means that the line is in the
kernel log of every boot of this kernel. Addresses are physical unless marked
KSEG1. The behaviours that a tested fact depends on are named in words: the
board boots to a shell; the watchdog is armed, fed and disarmed;
bridged traffic passes both ways, sourced from the host; the optics diagnostics
read, the laser is off before O3 and TX_DISABLE is honoured. "The stress run" is
a user-space program that repeats fork, exec, memory and unaligned-access checks
for a set time and compares every result with the expected one.

CPU core
========

The core is a Lexra LX5281. It runs big-endian and implements MIPS I with a
software-refilled, R3000-style TLB; user space is the o32 ABI. The kernel treats
it as an R3000 (``CPU_R3000``, reached through ``SYS_HAS_CPU_R3000``) and
departs from the generic R3000 code in three places:

- ``cpu_probe()`` recognises the core by its PRId and names it ``Lexra LX5281``.
- The caches are maintained through CP0 register 20 by
  ``arch/mips/mm/c-lexra.c``, because the R3000 cache code does not work on this
  core.
- A full TLB flush clears all 64 entries, not only entries 8 to 63.

MIPS I also sets limits that the rest of the kernel has to respect: the
exception vectors are fixed at ``0x80000000``, there is no ``sync`` instruction,
and the core's ``ll`` and ``sc`` cannot be used.

MIPS I limits the kernel respects
---------------------------------

.. warning::

   ``ll`` executes and returns the loaded value, but ``sc`` executes, never
   stores and always reports failure, and it never traps. Code built on ``ll``
   and ``sc`` does not crash on this core: it loops forever. The kernel emits
   neither, and user space must not either.

   :header-rows: 1
   :widths: 58 6 36

   * - Fact

       stores and always reports failure, and never traps. Code built on ``ll``
       and ``sc`` loops forever. The kernel emits neither (see "Identification
       and CPU class"); user space must not either.

   * - ``lwl``, ``lwr``, ``swl`` and ``swr`` execute and give the correct result

       must.

Caches
------

The R3000 cache code (``arch/mips/mm/c-r3k.c``) invalidates by isolating the
cache with Status.IsC and Status.SwC (bits 16 and 17) and storing bytes; it does
not work on this core. ``arch/mips/mm/c-lexra.c`` maintains the caches through
CP0 register 20, which MIPS I leaves unassigned, one operation word at a time.
Every operation acts on a whole cache.

   :header-rows: 1
   :widths: 58 6 36

``lexra_cache_init()``, in order
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

1. Install ``flush_cache_all`` and ``__flush_cache_all``: write back and
   invalidate the data cache, then invalidate the instruction cache. Purpose:
   whole-cache maintenance for the generic code. (T)
2. Install ``flush_cache_mm``: the same, skipped when the mm has no ASID on this
   CPU (``cpu_context() == 0``). Install ``flush_cache_range`` and
   ``flush_cache_page``: the same skip; otherwise the data cache, plus the
   instruction cache when the mapping is executable (``VM_EXEC``). Purpose: an
   mm that has never run on this CPU has nothing cached through its mappings
   (the rule of the R3000 code). (T)
3. Install ``flush_icache_range``, ``local_flush_icache_range``,
   ``__flush_icache_user_range`` and ``__local_flush_icache_user_range``: write
   the data cache back, then invalidate the instruction cache; the range is
   ignored. Purpose: instructions written through the data side must be in
   memory before the instruction cache refetches them, so the order matters. (T)
4. Install ``__flush_kernel_vmap_range`` and ``flush_data_cache_page``: write
   back and invalidate the data cache. (T)
5. Install ``_dma_cache_wback_inv`` and ``_dma_cache_inv``: write back and
   invalidate the data cache; install ``_dma_cache_wback``: write it back.
   Purpose: never an invalidate without write-back, and the hooks of the DMA
   API. (T)
6. Flush both caches. Purpose: put the caches in a known state before anything
   relies on them; what the boot loader leaves in them is not known. (I)
7. Call ``build_clear_page()`` and ``build_copy_page()``. Purpose:
   ``clear_page()`` and ``copy_page()`` are assembled at run time and made
   executable with the instruction-cache flush installed in step 3; until then
   the image holds a placeholder that jumps to itself. Every MIPS cache driver
   ends with these two calls. (M: without them the CPU enters the placeholder at
   the first ``__GFP_ZERO`` page allocation and never leaves it; with them the
   boot completes.)

TLB
---

The TLB has 64 entries and is refilled by software, as on the R3000; the refill
handler that ``tlbex.c`` generates for that TLB runs unchanged.
``r3k_wired_entries`` (``arch/mips/mm/tlb-r3k.c``) sets how many entries at the
bottom of the TLB a full flush leaves alone; on this core it is 0.

kexec
-----

``CONFIG_KEXEC`` builds for the platform and starts a new kernel on the
DFP-34X-2C3. The relocation code (``arch/mips/kernel/relocate_kernel.S``)
copies the new image through the cached segment. MIPS I has neither ``sync``
nor ``synci``, so with ``CONFIG_CPU_LEXRA_CACHE`` the code writes the data cache
back and invalidates it, then invalidates the instruction cache, through CP0
register 20 as ``c-lexra.c`` does, before it jumps to the new kernel.

The new kernel is given no command line of its own: registers a0 to a3 come
from ``kexec_args``, which no code of this platform fills in. The watchdog core
stops a running watchdog at a kexec as at a restart, unless the old kernel was
started with ``watchdog.stop_on_reboot=0``; then the watchdog keeps counting
across the jump, and a new kernel that hangs ends in a chip reset. The board's
configuration leaves kexec out. To run a development kernel without writing
flash, use the RAM boot described under "Boot contract"; the project's
``tools/kexec`` builds the RAM image with kexec on, a small target kernel and
the program that starts it (``tools/kexec/README.rst``).

Platform setup, restart and build
=================================

The platform code in ``arch/mips/rtl9602c/`` provides the hooks that the MIPS
architecture code calls. In the order in which the kernel reaches them:

1. ``cpu_probe()`` identifies the core (see "CPU core").
2. ``prom_init()`` (``setup.c``) builds the firmware command line from the boot
   loader's arguments.
3. ``setup_early_printk()`` starts the early console: from here
   ``prom_putchar()`` (``early_printk.c``) prints every character until the 8250
   driver takes over the console UART.
4. ``plat_mem_setup()`` (``setup.c``) adds the DRAM to memblock, hands the
   built-in device tree to the OF core, registers the console UART and installs
   halt and power off (the steps are listed below). It does not touch the
   watchdog: a count the boot loader armed for a trial boot runs on.
5. ``cpu_cache_init()`` calls ``lexra_cache_init()`` (see "Caches").
6. ``arch_init_irq()`` (``irq.c``) sets up the interrupt controller.
7. ``plat_time_init()`` (``setup.c``) registers the tree's clocks and probes
   the timers (see "Timers and the tick").
8. ``rtl9602c_populate_dt()`` (``arch_initcall``) creates the devices of the
   tree.
9. The drivers probe at ``device_initcall`` time; the watchdog driver takes
   over a watchdog the boot loader armed, and registers the restart handler.

Restart
-------

The platform installs no restart of its own: ``machine_restart()`` runs the
kernel's restart handlers, among them the watchdog driver's, which arms the
watchdog at its shortest deadline with a chip reset (see "Watchdog"). A kernel
without the watchdog driver cannot restart the board.

   :header-rows: 1
   :widths: 58 6 36

     - Tag

   * - The restart is a chip reset, not a jump to the boot loader's reset
       vector (``0xbfc00000``), which reaches the autoboot prompt sooner (1.81 s)

       switch then keeps the kernel's setup of the SFP lane, and behind the

Interrupt controller
====================

There are two levels. The CPU's eight interrupt lines are Linux interrupts 0 to
7 (``mips_cpu_irq_init()``). Behind line 2 sits a second-level controller with
64 sources, in two banks of 32, each with an enable and a status register. It
has no acknowledge register: a status bit clears when the device that raised it
is serviced, so the chip has only mask and unmask and every source is handled as
level-triggered. Sources 32 to 63 have no line of their own; they reach the CPU
through source 12 of the lower bank, which the driver enables once and never
masks. The controller is described by the ``intc`` node
(``realtek,rtl9602c-intc``); an interrupt specifier is one cell, the source
number.

     - Meaning

     - ``RTL9602C_INTC_EN(hw)`` for sources 0 to 31
     - Enable; a set bit lets the source through.

     - ``RTL9602C_INTC_EN(hw)`` for sources 32 to 63
     - Enable.
   * - ``+0x08``
     - ``RTL9602C_INTC_STAT(hw)`` for sources 0 to 31
     - Status; a bit is set while the source asserts, masked or not.
   * - ``+0x0c``
     - ``RTL9602C_INTC_STAT(hw)`` for sources 32 to 63

``arch_init_irq()``, in order
-----------------------------

1. Build-time checks of the numbering. Purpose: the fixed numbers must not
   collide. (T)
2. ``mips_cpu_irq_init()``. Purpose: the CPU's eight lines as Linux interrupts 0
   to 7. (T)
3. Write 0 to both enable registers. Purpose: start from silence; nothing is
   enabled that no driver asked for. (T)
4. Write ``0x22222222`` to the seven routing registers. Purpose: every source on
   CPU line 2. (M)
5. Create the legacy domain (64 sources at 8), anchored to the
   ``realtek,rtl9602c-intc`` node; panic if it cannot be created. Purpose: the
   numbering and the device tree translation. (T)
6. Enable source 12. Purpose: the way to sources 32 to 63. (M)
7. Chain the handler to CPU line 2. Purpose: this unmasks line 2 in Status. (T)

Timers and the tick
===================

MIPS I defines no CP0 Count and Compare registers, and the kernel uses none on
this core. The SoC's general-purpose timers have the layout of the Otto SoCs'
timers, and the Otto timer driver (``drivers/clocksource/timer-rtl-otto.c``,
``REALTEK_OTTO_TIMER``) takes them from the device tree: timer 0 as the clock
event device, periodic or one-shot, and timer 1 as the clocksource
``realtek_otto_timer`` and as sched_clock. Both count the LX bus clock divided
by 64, 3.125 MHz, so the clock has a resolution of 320 ns. The board's kernel
runs a periodic tick (``HZ_PERIODIC``, ``HZ`` = 250). ``plat_time_init()``
registers the tree's clocks (the fixed LX bus clock) and probes the timers.

UART and early console
======================

The console is UART0 at ``0x18002000``, a 16550A-compatible port whose registers
sit 4 bytes apart and are accessed as bytes. The boot loader leaves it at 115200
baud with divisor 109. Two pieces of platform code drive it. The early console
(``early_printk.c``) polls the UART directly from ``setup_early_printk()`` until
the 8250 driver takes over. ``rtl9602c_serial_init()`` (``setup.c``) registers
the port with ``early_serial_setup()``, so that the 8250 driver owns the console
and ``/dev/console``. The ``uart0`` node of the tree describes the same UART,
but no driver binds it.

Early console, ``prom_putchar()``
---------------------------------

The MIPS early console calls ``prom_putchar()`` for every character from
``setup_early_printk()`` onwards, before the 8250 driver exists; every boot
shows ``printk: legacy bootconsole [early0] enabled``, then ``disabled`` when
``ttyS0`` takes over. It must work where nothing else does, so it takes no lock
and never waits without a bound.

1. Read LSR (byte access) until ``UART_LSR_THRE`` is set, at most
   ``RTL9602C_UART_TX_POLL_MAX`` (30000) times. Purpose: a character may be
   written only into an empty holding register; the bound keeps a stuck
   transmitter from hanging the boot at a point where nothing can report it (the
   number is a software choice). (T)
2. If THRE came: write the character to THR (byte access). (T)
3. If the bound ran out: write ``RTL9602C_UART_FCR_TX_FIFO_RESET`` to FCR and
   drop the character. Purpose: an attempt to free a wedged transmitter. (I)

Watchdog
========

The watchdog block divides the 200 MHz LX bus clock into ticks and counts them
through two phases. The end of phase one sets a flag in the status register; the
end of phase two carries out the expiry action, which the device tree sets to a
reset of the whole chip. Writing the kick bit restarts the count. The block has
the registers of the Otto SoCs' watchdog without its interrupts, and the Otto
watchdog driver (``drivers/watchdog/realtek_otto_wdt.c``,
``REALTEK_OTTO_WDT``) drives it through the ``wdt`` node
(``realtek,rtl9602c-wdt``, the LX bus clock, ``realtek,reset-mode = "soc"``).

A watchdog the boot loader armed for a trial boot is kept running at probe and
fed by the watchdog core until user space opens ``/dev/watchdog``, for 60 s at
most (``WATCHDOG_OPEN_TIMEOUT``). Otherwise the driver leaves it off until
procd, the first process, opens the device and feeds it (ADR 0010). The driver
restarts the board through its restart handler, with the shortest deadline and
a chip reset, and offers no pretimeout, since the block raises no interrupt.
The platform code does not touch the watchdog.

   :header-rows: 1
   :widths: 10 34 56

   * - Offset
     - Register (driver's name)
     - Fields
   * - ``+0x00``
     - ``OTTO_WDT_REG_CNTR``
     - Bit 31 ``OTTO_WDT_CNTR_PING`` restarts the count.
   * - ``+0x04``
     - ``OTTO_WDT_REG_INTR``
     - Bit 31 ``OTTO_WDT_INTR_PHASE_1``: phase one has expired.
   * - ``+0x08``
     - ``OTTO_WDT_REG_CTRL``
     - ``OTTO_WDT_CTRL_ENABLE`` (bit 31), ``OTTO_WDT_CTRL_PRESCALE`` (bits
       30:29), ``OTTO_WDT_CTRL_PHASE1`` (bits 26:22),
       ``OTTO_WDT_CTRL_PHASE2`` (bits 19:15), ``OTTO_WDT_CTRL_RST_MODE``
       (bits 1:0). All other bits hold nothing.

GPIO and pad control
====================

The SoC's GPIO bank is driven by the Otto GPIO driver
(``drivers/gpio/gpio-realtek-otto.c``, ``CONFIG_GPIO_REALTEK_OTTO``), unchanged
apart from one match entry for ``realtek,rtl9602c-gpio``. On this board one line
is used: line 13, the laser driver's TX_DISABLE input (see the facts below),
which the laser driver's driver, ``gn25l95``, requests through
``tx-disable-gpios`` on its node in the switch's ``i2c`` node. Two pad-function
registers in the
switch register window route pins to their functions:
``RTL9602C_PADMUX_GPIO_EN`` selects GPIO use per pin, and
``RTL9602C_PADMUX_FUNC_EN`` enables other functions, the I2C masters among them.

Flash and partitions
====================

The board's flash is an 8 MiB SPI NOR chip on the SoC's SPI controller. The SoC
also maps the whole chip into physical memory at ``0x14000000``-``0x147fffff``
for reading, and the boot loader starts a kernel from that window in place.
Linux leaves the window unused and reaches the chip through the controller,
which can erase and program it: the tree describes the chip as ``flash@0``, with
``compatible = "jedec,spi-nor"``, on ``spi``. Its partitions are the boot
loader's own layout. The kernel and the root filesystem of two banks sit in
``k0`` and ``r0`` (bank 0) and ``k1`` and ``r1`` (bank 1), and either holds this
system: an update goes into the bank the system did not start from. Only the
boot loader, ``boot``, is read-only.

The partitions are the eight of the board's device tree,
``arch/mips/boot/dts/realtek/dfp-34x-2c3.dts``, which gives each its offset
and its size; the project's handbook lists them, with what each holds and who
writes it, in ``docs/handbook/boot-contract.rst``.

Boot contract
=============

The boot loader, a U-Boot of the 2011.12 release (its banner says so on every
reset), lives in the ``boot`` partition and starts the kernel. This chapter
states the contract between the two as an interface: what the kernel image must
look like, how it is entered, what it is handed and what it finds when it
starts.

.. list-table::
   :header-rows: 1
   :widths: 58 6 36

   * - Fact
     - Tag
     - Checked by
   * - Image: a legacy U-Boot image of the raw kernel, LZMA-compressed; the boot
       loader checks and decompresses it itself, so the kernel selects
       ``HAVE_KERNEL_LZMA`` and no self-extracting wrapper. Header: MIPS, Linux,
       kernel, lzma; load address ``0x80100000``; entry point the address of
       ``kernel_entry``.
     - M
     - Every boot: the boot loader prints ``Image Type: MIPS Linux Kernel Image
       (lzma compressed)``, ``Load Address: 80100000``, the entry point, and
       ``Uncompressing Kernel Image ... OK``.
   * - The load address comes from ``Platform``: ``load-$(CONFIG_RTL9602C) +=
       0xffffffff80100000``, the sign-extended KSEG0 address of physical
       ``0x00100000``. The kernel must lie above the fixed exception vectors at
       ``0x80000000``-``0x800003ff`` (see "MIPS I limits the kernel respects");
       1 MiB up is the usual choice in arch/mips.
     - M, T
     - M: linked at ``0x80000000`` the kernel stops in ``trap_init()``; at
       ``0x80100000`` it boots. T: comparing the load address in the built
       image's header with ``Platform`` catches a difference.
   * - ``CONFIG_PHYSICAL_START``, which the architecture offers once
       ``CRASH_DUMP`` is on (and ``KEXEC`` turns ``CRASH_DUMP`` on by default),
       overrides the platform's load address; its default puts the kernel at
       physical ``0x04000000``, above this board's 32 MiB. The configuration
       keeps ``CRASH_DUMP`` off.
     - M
     - Turning ``KEXEC`` on moves the image header's load address from
       ``0x80100000`` to ``0x84000000`` with no other change; the header
       comparison above catches it.
   * - Entry: the boot loader jumps to the entry point with ``a0`` = argument
       count, ``a1`` = pointer to an argument vector (``argv[0]`` unused),
       ``a2`` = environment pointer (the MIPS convention of U-Boot's ``bootm``);
       ``kernel_entry`` saves them as ``fw_arg0``-``fw_arg3``.
       ``fw_init_cmdline()`` accepts them when ``a0`` < ``0x80000000`` and
       ``a1`` >= ``0x80000000``, and joins ``argv[1]`` and the following
       arguments with spaces. The environment is not used. ``BOOT_RAW`` also
       puts a jump to ``kernel_entry`` at the load address, so an image entered
       at its load address starts too; this boot loader enters at the entry
       point.
     - M, T
     - M: every boot, the boot loader's arguments appear in
       ``Kernel command line:``. T: the board boots to a shell.
   * - The boot loader passes no device tree; the kernel carries this board's
       (``USE_OF``, ``BUILTIN_DTB``).
     - T
     - The board boots to a shell.
   * - Command line: the tree's ``/chosen/bootargs`` (``panic=10``), then the
       boot loader's arguments. For bank 0 those are ``console=ttyS0,115200``,
       an ``mtdparts=`` table for the boot loader's own flash naming, which this
       kernel ignores (the partitions come from the tree and no command-line
       partition parser is built), and ``root=31:5``; bank 1's are the same with
       ``root=31:7``.
     - M, I
     - M: the boot loader's arguments, every boot, in ``Kernel command line:``
       and in the boot loader's environment; a start of bank 1 mounted its root
       filesystem as 31:7. I: their order after ``panic=10``; see the row on
       ``chosen``.
   * - Which bank a plain reset boots is set in the boot loader's environment: a
       committed bank, and a one-shot mode that arms the watchdog before booting
       so that a failing image costs one reset. A flash boot loads the image
       from the flash window in place (KSEG0 ``0x94080000`` for bank 0,
       ``0x94440000`` for bank 1). The kernel itself does not change the
       choice; user space does, through the writable ``env`` and ``env2``.
     - M
     - The boot loader's environment, read at its prompt and from the ``env``
       partition; a one-shot start of bank 1 armed from Linux booted the image
       at ``0x94440000``.
   * - The kernel's first act in ``plat_mem_setup()`` clears the watchdog, which
       also ends a one-shot boot's watchdog; from the watchdog driver's probe
       on, the kernel feeds the watchdog until user space opens it. A one-shot
       boot whose kernel hangs before that probe, or whose user space never
       opens the watchdog, is therefore not reset by it.
     - I
     - Not observed; a one-shot boot of a kernel that stops early would show.
   * - Restart: the kernel has the watchdog reset the chip, the boot loader
       starts and counts down to autoboot, then boots the committed bank unless
       interrupted at the console.
     - M
     - In three restarts: 1.9 s from the restart's console line to the first
       stage's banner, 3.1 s to the ``U-Boot`` banner and about 3.2 s to the
       autoboot prompt.

RAM boot over TFTP
------------------

This is the way to run a development kernel. Nothing is written to flash, and a
kernel that fails costs one reset.

1. Stop the autoboot countdown at the console. Purpose: the board is at the boot
   loader prompt. (M)
2. Bring the host link up. Purpose: the boot loader's network interface is the
   switch's SerDes, and it leaves the SerDes off (mode field ``0x1f`` in
   ``RTL9602C_SERDES_CTRL``); the same 2500BASE-X bring-up that the switch
   driver performs has to be written from the prompt, for instance by a macro in
   the boot loader's saved environment. (M)
3. ``tftpboot 0x81000000 uImage``. Purpose: the image into DRAM at physical 16
   MiB. (M)
4. Set the boot arguments to bank 0's. Purpose: the kernel gets its usual
   command line. (M)
5. ``bootm 0x81000000``. Purpose: the boot loader checks the image, decompresses
   it to ``0x80100000`` and enters it. (M)

The commands of steps 3 and 5::

   tftpboot 0x81000000 uImage
   bootm 0x81000000

.. list-table::
   :header-rows: 1
   :widths: 58 6 36

   * - Fact
     - Tag
     - Checked by
   * - The macro and the network settings must be in the saved environment: a
       setting made without saving is gone after the next reset.
     - M
     - A setting made without saving does not survive the reset.
   * - The image is decompressed to 1 MiB while its compressed copy sits at 16
       MiB, so the decompressed kernel must end below physical ``0x01000000``
       (15 MiB of room). The boot loader may also cap the decompressed size, at
       a limit not known. A development kernel of about 8 MB decompressed fits.
     - I
     - Arithmetic, not tested at the limit; the size is the sum of code, rwdata,
       rodata and init in the kernel's ``Memory:`` line. RAM-boot images of
       growing size until one fails would show.
   * - What the boot loader leaves for the kernel: UART0 at 115200 baud with
       divisor 109; timer 1 running with control ``0x11000032``, which the
       kernel sets up again as its clock; the SerDes
       off unless the RAM boot's second step ran; the system controller's PON
       packet-buffer enable clear (``RTL9602C_SYSCTL_BLOCK_EN`` at ``+0x63c``
       reads ``0x10``); the watchdog disarmed unless a one-shot boot, or an
       older kernel's restart by a jump, armed it.
     - M
     - Every boot for the divisor; timer 1 and the SerDes control register
       (``0x0004801f`` at the prompt) read at the boot loader prompt; the system
       controller register read; the watchdog as in the row on the count that
       outlives a restart.

Open questions
==============

These are the facts tagged **I** in the tables above, each with what would
settle it. The first list holds the assumptions the driver depends on: the
kernel is correct on this board only if they hold. The second list holds the
questions to which the code is indifferent: it works whichever way they resolve.

Assumptions the driver depends on
---------------------------------

.. list-table::
   :header-rows: 1
   :widths: 58 42

   * - Assumption
     - What would settle it
   * - An uncached load drains the write buffer, so ``mb()`` and ``iob()`` order
       device writes ("MIPS I limits the kernel respects").
     - A store to a device register, then a read back through an uncached load
       of a register that reflects the store.
   * - The TLB has exactly 64 entries ("TLB").
     - ``tlbwi`` and ``tlbr`` over indices 0 to 64.
   * - A trial boot that hangs before the watchdog driver's probe is reset by
       the count the boot loader armed, which the kernel no longer stops
       ("Watchdog").
     - A deliberate hang in that stretch during a trial boot of the boot
       loader.
   * - The PON MAC's DMA stays inside each reserved region. Whether it uses the
       4 KiB past the programmed 1 MiB is unknown, so that 4 KiB is kept ("DRAM
       and reserved memory").
     - Shrinking both regions to ``0x100000`` and repeating the downstream-lock
       and OMCI checks.
   * - The placement of the two regions is acceptable to the PON MAC ("DRAM and
       reserved memory").
     - Moving the downstream region and repeating the same checks.
   * - Bit 13 of ``RTL9602C_PADMUX_GPIO_EN`` is needed to route pad 13 to its
       GPIO function: with it set the line acts on the laser ("Pad control").
     - A run with the bit clear.
   * - The decompressed kernel stays below 15 MiB and below whatever cap the
       boot loader has ("RAM boot over TFTP").
     - RAM-boot images of growing size until one fails.
