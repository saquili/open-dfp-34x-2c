========================
rtl9602c devlink support
========================

This document describes the devlink features implemented by the ``rtl9602c``
device driver, the DSA driver of the switch of the Realtek RTL9602C, the SoC of
GPON optical network units such as SFP sticks. The switch and its driver are
described in Documentation/networking/dsa/rtl9602c.rst. This page is what a
user needs to drive the switch through ``devlink``: how to address the device,
every driver-specific parameter, the region and the reply of the info command.

Overview
========

The driver implements these devlink objects and no others:

- 22 driver-specific parameters, all of mode ``runtime``. They configure the
  malformed-frame (DoS) checks, the four storm-control classes that ``tc``
  cannot describe, the header capture, loop detection and the ONU's serial
  number (see "Parameters").
- One region, ``frame_capture``, that holds a snapshot of the header capture
  (see "The region frame_capture").
- The reply to ``devlink dev info``, which names the part and the revision of
  the GPON MAC (see "Device info").

The driver registers no generic parameters, resources, traps, health reporters
or shared buffers, and it does not support reload. DSA creates the devlink
ports of the switch, and the driver adds nothing to them. The speed and the
in-band negotiation of the SerDes lane to the host are module parameters,
``rtl9602c.sfp_mode`` and ``rtl9602c.sfp_an``, and not devlink parameters;
Documentation/networking/dsa/rtl9602c.rst describes them.

The hardware behind the parameters is described on these pages, which the
sections below name again where a parameter uses them:

- Documentation/networking/dsa/rtl9602c-acl-qos.rst: the DoS checks, the meters
  and storm control, loop detection and the header capture.
- Documentation/networking/dsa/rtl9602c-bridging.rst: the reserved group
  addresses that storm control leaves alone.
- Documentation/networking/dsa/rtl9602c.rst: the switch core, the ports, the
  identification of the part, setup and reload, and the system controller.
- Documentation/networking/device_drivers/pon/rtl9602c-gpon.rst: the GPON MAC
  and what the ONU's serial number is used for.
- Documentation/networking/pon.rst: the PON class, which reports the serial
  number in the status of the PON device.
- Documentation/networking/dsa/rtl9602c-ptp.rst: the PTP clock, which has no
  devlink object.

The handle
----------

The devlink instance is the platform device of the ``switch`` node of the
device tree, compatible ``realtek,rtl9602c-switch``, unit address
``1b000000``. Its handle is ``platform/1b000000.switch``, and every command on
this page uses it::

    # devlink dev show
    platform/1b000000.switch

The platform driver and the module are named ``rtl9602c``, which is the driver
name in the reply of ``devlink dev info``. The driver creates its parameters
and its region in ``rtl9602c_setup()``, which DSA calls when the switch is
registered, and removes them in ``rtl9602c_teardown()``.

The code
--------

The driver implements three operations of ``struct dsa_switch_ops`` for
devlink, ``devlink_info_get``, ``devlink_param_get`` and ``devlink_param_set``
(every name is prefixed ``rtl9602c_``), and creates the region with
``dsa_devlink_region_create()``.

Configuration and device tree
-----------------------------

``CONFIG_NET_DSA_RTL9602C`` builds everything on this page, as
Documentation/networking/dsa/rtl9602c.rst describes. Devlink itself is
``CONFIG_NET_DEVLINK``, which ``CONFIG_NET_DSA`` selects. No device tree
property configures devlink: the ``switch`` node only gives the handle.

Interfaces to user space
------------------------

- ``devlink dev show`` and ``devlink dev info platform/1b000000.switch``.
- ``devlink dev param show`` and ``devlink dev param set`` on the 22
  parameters.
- ``devlink region show``, ``new``, ``read``, ``dump`` and ``del`` on
  ``platform/1b000000.switch/frame_capture``.
- The kernel log lines that begin ``rtl9602c-switch:``. The ones this page
  names are ``devlink parameters unavailable; the switch's own features cannot
  be configured``, ``no devlink region; frames cannot be captured`` and
  ``<GPON> serial number set``.

How to read the fact tables
===========================

The parameters are described in tables with the columns *Name*, *Type*, *Mode*
and *Description*, as on every devlink page. The description gives the range of
the value, what it controls, whether a read comes from the hardware or from the
driver's copy, and the error that a bad value gets. After them, and for the
region and the info reply, fact tables with three columns, *Fact*, *Tag* and
*Checked by*, say how a behaviour is established. The tag says how. **M**,
measured on the board (the DFP-34X-2C3): *Checked by* gives the command or
observation, through the driver's own interfaces (``devlink``, the kernel log,
``ip``), that shows it. **T**, tested by function: the driver depends on the
fact, and the named behaviour fails if it is wrong. **P**, public standard:
*Checked by* names the document and the clause. **I**, inferred, not verified:
the fact is an assumption, and *Checked by* says what would confirm or refute
it. The last chapter collects these facts. A row with two tags is established
in two ways, or in two parts; *Checked by* says which part carries which tag.

Port numbers are the hardware's (0 ``sfp``, 1 not wired, 2 ``pon``, 3 the CPU
port; see Documentation/networking/dsa/rtl9602c.rst), and "the host" is the
equipment at the far end of the SFP lane. The behaviours that a tested fact
depends on are named in words: the board boots to a shell; the ONU reaches O5
on an OLT; the storm-control rates match their settings.

Parameters
==========

All 22 parameters are driver-specific, of type u8, u32 or string, and of mode
``runtime``: a value takes effect at once. There are six for the DoS checks,
eight for storm control, four for the header capture, three for loop detection
and one for the ONU's serial number. The driver registers them at setup. If it
cannot, it logs ``devlink parameters unavailable; the switch's own features
cannot be configured`` and the switch carries on without them.

Reading and setting
-------------------

``devlink dev param show`` reads a parameter and ``devlink dev param set``
writes it. The mode must be given, and only ``runtime`` is offered: a set with
``driverinit`` or ``permanent`` is refused with ``-EOPNOTSUPP``::

    devlink dev param show platform/1b000000.switch
    devlink dev param show platform/1b000000.switch name dos_checks
    devlink dev param set platform/1b000000.switch \
            name dos_checks value 6 cmode runtime

The second command prints::

    platform/1b000000.switch:
      name dos_checks type driver-specific
        values:
          cmode runtime value 6

Four rules hold for every parameter:

- A value is read when it is asked for, either from the hardware or from the
  driver's copy of what it last wrote; the tables say which. A read from the
  hardware shows a change made behind the driver's back. A read from the copy
  shows what was set.
- The range of every value is checked in the driver's set callback, because
  DSA's parameter macro leaves the validate callback empty. A value too wide
  for its field is refused with ``-ERANGE`` ("Numerical result out of range")
  and never cut to fit. Devlink itself refuses a value of the wrong type, and
  a string of 32 characters or more, with ``-EINVAL`` before the driver sees
  it.
- A refusal carries an error number and no text: a parameter set has no
  message channel. The tables give the number of each refusal.
- A port mask has four bits, bit p for port p: 1 is port 0 (``sfp``), 4 is
  port 2 (``pon``), 8 is port 3 (the CPU port), and 15 is all of them. Port 1
  is not wired.

State, defaults and reload
--------------------------

A warm restart of the CPU and a reload of the module leave the switch running
with its registers as they were. The driver therefore writes the state that the
parameters control every time it probes, and the parameters start from the
defaults that the tables give: the DoS checks off with their thresholds at 0;
storm control off with every meter free; loop detection off; the header
capture armed in mode 1, which never captures, with both port masks 15 and
reason 0; and no serial number. The one exception is ``loop_detect_period``,
which setup does not write, so it keeps the value it had. Nothing is saved:
after a reboot or a reload of the module the parameters are back at their
defaults, and the serial number is empty.

DoS checks
----------

The switch can recognise sixteen shapes of malformed or hostile frames,
numbered 0 to 15, and drop them or deliver them to the CPU. A check acts on a
frame only when the frame enters a port set in ``dos_ports`` and the check's
bit is set in ``dos_checks``. ``dos_actions`` chooses, check by check, between
dropping the frame and delivering it to the CPU, and the three flood checks
have a threshold each. The checks, the forwarding reason that each produces and
the registers are on Documentation/networking/dsa/rtl9602c-acl-qos.rst
("Malformed-frame (DoS) checks").

.. list-table::
   :header-rows: 1
   :widths: 22 6 8 64

   * - Name
     - Type
     - Mode
     - Description
   * - ``dos_ports``
     - u32
     - runtime
     - The ports whose entering frames the checks judge, as a port mask: 0 to
       15 (``0xf``). Default 0. Read from ``RTL9602C_DOS_PORT_EN``. A value
       above 15 is refused with ``-ERANGE``.
   * - ``dos_checks``
     - u32
     - runtime
     - Enables the checks, bit n for check n: 0 to 65535 (``0xffff``). Bit 1 is
       land and bit 2 is blat; the other bits are listed in
       Documentation/networking/dsa/rtl9602c-acl-qos.rst. Default 0. Read from
       the enable half of ``RTL9602C_DOS_CHECK_CTRL``. A value above 65535 is
       refused with ``-ERANGE``.
   * - ``dos_actions``
     - u32
     - runtime
     - What a check does with the frame it stops, bit n for check n: 0 to 65535
       (``0xffff``). A bit of 0 drops the frame, a bit of 1 delivers it to the
       CPU instead of forwarding it. Default 0, so every check drops. Read
       from the action half of ``RTL9602C_DOS_CHECK_CTRL``. A value above
       65535 is refused with ``-ERANGE``.
   * - ``dos_synflood_thresh``
     - u8
     - runtime
     - The threshold of check 13, the SYN flood: 0 to 255, a count of matching
       frames over a hardware window of unknown length. At 0 the check fires
       on the first matching frames. Default 0. Read from the driver's copy of
       the last value written; the register is never read. Every u8 value is
       valid.
   * - ``dos_finflood_thresh``
     - u8
     - runtime
     - The threshold of check 14, the FIN flood; otherwise as
       ``dos_synflood_thresh``.
   * - ``dos_icmpflood_thresh``
     - u8
     - runtime
     - The threshold of check 15, the ICMP flood; otherwise as
       ``dos_synflood_thresh``.

To judge the frames entering ``sfp`` for land and blat, and to drop the frames
these checks stop::

    devlink dev param set platform/1b000000.switch \
            name dos_ports value 1 cmode runtime
    devlink dev param set platform/1b000000.switch \
            name dos_checks value 6 cmode runtime

Setting ``dos_actions`` to 6 as well would deliver those frames to the CPU
instead.

Storm control
-------------

Storm control limits the rate of a class of frames entering a port by giving
the class one of the sixteen shared meters. ``tc`` reaches three classes,
broadcast, multicast and ARP. Devlink reaches the other four, each with a rate
in packets per second and a mask of the ports it applies to: unknown unicast,
unknown multicast, DHCP, and IGMP with MLD. Unknown unicast is unicast to an
address that the switch has not learned, and unknown multicast is multicast to
a group that no table holds; the five reserved group addresses of spanning
tree, pause, the Slow Protocols, 802.1X and LLDP are exempt from the
unknown-multicast limit. The meters are one pool, shared with the storm-control
rules of ``tc``. The meters, their unit and the classes are on
Documentation/networking/dsa/rtl9602c-acl-qos.rst ("Storm control"), and the
exempt addresses on Documentation/networking/dsa/rtl9602c-bridging.rst.

Set the rate first and the ports second: a port mask is refused while the class
has no rate. A rate of 0 switches the class off on every port and gives the
meter back.

Header capture
--------------

The header capture freezes one frame: the parser's view of it and the switch's
decision about it. ``pktdbg_mode`` chooses which frame, ``pktdbg_ingress_ports``
and ``pktdbg_egress_ports`` restrict it by port, and ``pktdbg_reason`` is the
forwarding reason that mode 7 waits for. The four make up one setting: setting
any of them re-arms the capture with all four, which discards the frame it
held. The frame is read as a snapshot of the region ``frame_capture`` (see "The
region frame_capture"). The capture is described on
Documentation/networking/dsa/rtl9602c-acl-qos.rst ("Frame capture").

   :header-rows: 1
   :widths: 22 6 8 64

   * - Name
     - Type
     - Mode
     - Description
   * - ``pktdbg_mode``
     - u8
     - runtime
     - Which frame the capture holds: 0 any frame; 1 none, the capture never
       latches; 2 the first dropped frame; 3 the first forwarded frame; 4 the
       first frame delivered to the CPU; 5 dropped frames; 6 frames delivered
       to the CPU; 7 frames whose forwarding reason is ``pktdbg_reason``.
       Modes 3 and 4 have not been exercised. Default 1. Read from the
       driver's copy. A value above 7 is refused with ``-ERANGE``.
   * - ``pktdbg_ingress_ports``
     - u8
     - runtime
     - The ingress ports whose frames the capture may latch, as a port mask: 0
       to 15 (``0xf``). Default 15. Read from the driver's copy. A value above
       15 is refused with ``-ERANGE``.
   * - ``pktdbg_egress_ports``
     - u8
     - runtime
     - The egress ports whose frames the capture may latch, as a port mask: 0
       to 15 (``0xf``). Default 15. Read from the driver's copy. A value above
       15 is refused with ``-ERANGE``.
   * - ``pktdbg_reason``
     - u8
     - runtime
     - The forwarding reason that mode 7 waits for: 0 to 255. The other modes
       ignore it. Default 0. Read from the driver's copy. Every u8 value is
       valid.

Loop detection
--------------

Loop detection sends probe frames out of the chosen ports at a fixed interval
and reports a port on which one of its own probes comes back, and when the loop
has gone. The driver only reports, in the kernel log; deciding what to do about
a loop is left to the bridge's spanning tree. The probe, its magic, the
registers and the log lines are on
Documentation/networking/dsa/rtl9602c-acl-qos.rst ("Loop detection").

.. list-table::
   :header-rows: 1
   :widths: 22 6 8 64

   * - Name
     - Type

     - Description
   * - ``loop_detect``

       enable bit of ``RTL9602C_LOOPDET_CTRL``. A value above 1 is refused with

GPON serial number
------------------

The ONU presents a serial number to the OLT in activation. The driver has none
of its own: until ``gpon_serial`` is set, the parameter reads empty, the
serial-number message is not armed, and bringing the ``pon`` interface up fails
with ``-ENXIO``. The GPON MAC and the use of the serial number are on
Documentation/networking/device_drivers/pon/rtl9602c-gpon.rst. The PON class
reports the same serial number in the status of the PON device
(Documentation/networking/pon.rst).

.. list-table::
   :header-rows: 1
   :widths: 22 6 8 64

   * - Name
     - Type
     - Mode
     - Description
   * - ``gpon_serial``
     - string
     - runtime
     - The serial number of the ONU: four characters of Vendor_ID followed by
       eight hexadecimal digits that give the four octets of the vendor-specific
       serial number, for example ``ABCD12345678``. A value needs at least 12
       characters. The first four must be printable ASCII (``0x20`` to
       ``0x7e``) and the next eight hexadecimal digits, in either case;
       characters after the twelfth are ignored, and anything else is refused
       with ``-EINVAL``. A set while the ``pon`` interface is up is refused
       with ``-EBUSY``. A valid value is kept, the kernel log says ``<GPON>
       serial number set``, and the serial-number message is armed at once.
       Reads empty until a serial number has been set, then the four characters
       and the eight digits in upper case, from the driver's copy.
   * - ``gpon_password``
     - string
     - runtime
     - The password the ONU gives when the OLT asks for it with
       Request_Password: one to ten printable ASCII characters, padded with
       zero octets to the ten of the Password message, or ``0x`` followed by
       twenty hexadecimal digits that give the ten octets themselves. An empty
       value forgets it. A longer or malformed value is refused with
       ``-EINVAL``, and a set while the ``pon`` interface is up with
       ``-EBUSY``. A valid value is kept and the kernel log says ``<GPON>
       password set``. Reads ``set`` once a password is kept and empty
       otherwise, never the password itself.

To set the serial number, read it back and bring the interface up::

    devlink dev param set platform/1b000000.switch \
            name gpon_serial value ABCD12345678 cmode runtime
    devlink dev param show platform/1b000000.switch name gpon_serial
    ip link set pon up

The region frame_capture
========================

The region ``frame_capture`` holds a snapshot of the header capture: the frame
that the capture holds, as the parser saw it and as the switch decided about it.
A snapshot is taken on demand with ``devlink region new``. The capture is armed
with the ``pktdbg_*`` parameters (see "Header capture"). If the driver cannot
create the region it logs ``no devlink region; frames cannot be captured`` and
the switch carries on without it.

.. list-table::
   :header-rows: 1
   :widths: 24 16 16 44

   * - Region
     - Size
     - Snapshots
     - What it holds
   * - ``frame_capture``
     - 168 bytes
     - 1, at most
     - The control word of the capture, the parser's view of the frame and the
       switch's verdict on it.

Taking, reading and deleting a snapshot
---------------------------------------

The region is listed, a snapshot is taken with an id of the caller's choice,
read whole, dumped and deleted with::

    devlink region show platform/1b000000.switch/frame_capture
    devlink region new platform/1b000000.switch/frame_capture snapshot 1
    devlink region read platform/1b000000.switch/frame_capture snapshot 1 \
            address 0 length 168
    devlink region dump platform/1b000000.switch/frame_capture snapshot 1
    devlink region del platform/1b000000.switch/frame_capture snapshot 1

``devlink region show`` prints the size and the snapshots that exist::

    platform/1b000000.switch/frame_capture: size 168 snapshot [] max 1

Without a snapshot id in ``devlink region new`` the kernel chooses one and the
tool prints it. A snapshot is refused with ``-EAGAIN`` ("Resource temporarily
unavailable") while the capture holds no frame, with the message ``rtl9602c:
nothing is latched: arm pktdbg_mode and offer the switch some traffic``, so a
snapshot always describes a frame. The region keeps one snapshot at a time (see
"Known limitations").

What a snapshot holds
---------------------

A snapshot is 42 words (``RTL9602C_PKTDBG_SNAPSHOT_WORDS``), each in the CPU's
byte order, which is big-endian: the most significant byte of a word comes
first in a dump. Bit b of the parse or of the verdict is bit b mod 32 of word
number b / 32, rounded down, of that part.

.. list-table::
   :header-rows: 1
   :widths: 14 26 60

   * - Bytes
     - Content
     - Fields
   * - 0 to 3
     - The control word, ``RTL9602C_PKTDBG_LATCH`` as it was armed.
     - Mode (bits 4:2), ingress port mask (8:5), egress port mask (12:9),
       forwarding reason (20:13) and VALID (21), which is set in every
       snapshot.
   * - 4 to 115
     - The parse, ``RTL9602C_PKTDBG_PARSE(0..27)``: 28 words, the parser's view
       of the frame.
     - Bits 13:0 of the parse, in bytes 4 to 7, are the frame length.
   * - 116 to 167
     - The verdict, ``RTL9602C_PKTDBG_VERDICT(0..12)``: 13 words, the switch's
       decision.
     - Verdict bits 331:324 are the destination port mask, 0 for a dropped
       frame, and bits 346:339 the forwarding reason. Both are in verdict word
       10, bytes 156 to 159: the mask in its bits 11:4 and the reason in its
       bits 26:19.

The forwarding reasons that were measured are 0, an ordinary forward; 64 + n, a
frame stopped by DoS check n; 88, a drop by storm control; and 228, a
destination that resolves to the port the frame entered by. The others are
listed in Documentation/networking/dsa/rtl9602c-acl-qos.rst ("Frame capture").

   :header-rows: 1
   :widths: 58 6 36

   * - Fact

Worked example: why was a frame dropped
=======================================

This limits unknown multicast to one packet per second on ``sfp``, asks the
capture for dropped frames, and reads the verdict on a frame that the limit
dropped. The rate comes first, then the ports, because the ports are refused
while the class has no rate::

    devlink dev param set platform/1b000000.switch \
            name storm_unknown_multicast_pps value 1 cmode runtime
    devlink dev param set platform/1b000000.switch \
            name storm_unknown_multicast_ports value 1 cmode runtime
    devlink dev param set platform/1b000000.switch \
            name pktdbg_mode value 5 cmode runtime

Now the host sends a burst of frames to a multicast group that no table holds,
for example 01:00:5e:01:02:03. Mode 5 holds a dropped frame, and the snapshot
names it::

    devlink region new platform/1b000000.switch/frame_capture snapshot 1
    devlink region read platform/1b000000.switch/frame_capture snapshot 1 \
            address 0 length 4
    devlink region read platform/1b000000.switch/frame_capture snapshot 1 \
            address 156 length 4
    devlink region del platform/1b000000.switch/frame_capture snapshot 1

The first read returns the control word as armed. For mode 5 and the default
port masks it is ``0x00201ff4``, so the four bytes are ``00 20 1f f4``. The
second read returns verdict word 10. For a frame dropped by storm control,
bits 11:4 of the word, the destination port mask, are 0, and bits 26:19, the
forwarding reason, are 88 (``0x58``). Another reason means that the capture
held some other dropped frame. To capture another frame, set any of the
``pktdbg_*`` parameters again, even to the value it has: that re-arms the
capture.

Known limitations
=================

- The region keeps one snapshot. A second ``devlink region new`` is refused
  with ``-ENOSPC`` until the first has been deleted with ``devlink region
  del``. The snapshot is kept in memory, and it goes with the region when the
  driver is unloaded.
- The region can be read only through a snapshot. ``devlink region read`` and
  ``dump`` without a snapshot id are refused with ``-EOPNOTSUPP``.
- The capture holds no frame in mode 1, which is the mode after setup, and
  after a change of any ``pktdbg_*`` parameter until a frame of the chosen kind
  arrives: each change re-arms the capture and discards the frame it held. A
  snapshot taken then is refused.
- The ``pktdbg_*`` parameters and the flood thresholds answer from the driver's
  copy of what it last wrote, so they do not show a change made to the
  registers behind the driver.
- Nothing set through devlink survives a reboot or a reload of the module. The
  serial number has to be set again before the ``pon`` interface is brought up,
  and it cannot be changed while that interface is up.
- A port mask for a storm-control class is refused until the class has a rate,
  and setting the rate of a class to 0 also clears its ports.
- Setting ``loop_detect`` changes the switch's interrupt mask by a read
  followed by a write, under no lock that the interrupt handler and the other
  writers of the mask share, so a change made by two of them at the same moment
  could be lost. This has not been observed. It is stated in full in
  Documentation/networking/dsa/rtl9602c.rst ("Known limitations").
