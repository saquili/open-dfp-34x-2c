=======================
Realtek RTL9602C switch
=======================

Overview
========

The RTL9602C is a SoC for GPON optical network units, such as SFP sticks. Its
Ethernet switch has four ports. Port 0 is a SerDes lane to the host, the
equipment the stick is plugged into. Port 1 exists in the silicon and is not
wired on this board. Port 2 is the PON port, behind which the PON MAC and the
GPON MAC sit, and beyond them the optics and the fibre. Port 3 is the CPU port,
which ends in a DMA engine: the conduit of DSA.

The switch's register window, physical ``0x1b000000``, is larger than the
switch core. It also holds the GPON MAC, the PON MAC with its packet buffer,
the L3/NAT engine, the IEEE 1588 clock and the I2C masters of the optics, and
one driver, ``rtl9602c``, drives all of it. The driver is a DSA driver for the
switch, and it registers the GPON side with the PON class
(Documentation/networking/pon.rst). This page describes the switch core as the
driver sets it up: probe and identification, the forced MAC ability of the
ports, the SerDes lane to the host and phylink, the switch's half of the CPU
tag, the frame length limit, the switch's interrupt, the per-port counters,
restart and teardown, the order of setup, and the enable in the system
controller in front of the PON packet buffer. The other blocks have pages of
their own (see "Where to read next").

The wiring of the ports::

    host cage
       |  SFP edge connector, SerDes lane, 2500BASE-X or 1000BASE-X
    port 0 (sfp)
    +--------------+  port 3 (CPU)   +----------------+
    | switch core  |-----------------| DMA engine     |--- LX5281 CPU
    +--------------+                 | (cpu, conduit) |
    port 2 (pon)                     +----------------+
       |
    PON MAC, GPON MAC
       |
    optics, fibre

How the driver plugs into DSA
-----------------------------

The driver is a platform driver named ``rtl9602c``, matched by the compatible
``realtek,rtl9602c-switch``. ``rtl9602c_probe()`` describes the switch to DSA
(the number of ports, the operations ``rtl9602c_switch_ops``, the phylink MAC
operations, VLAN filtering that is switch-wide and the ageing range) and calls
``dsa_register_switch()``. DSA then calls ``rtl9602c_setup()`` (see "Setup, in
order"). Three things are particular to this switch:

- The tag protocol is ``DSA_TAG_PROTO_RTL9602C``, and
  ``rtl9602c_get_tag_protocol()`` returns it for every port. The CPU tag does
  not travel in the frame but in the descriptors of the CPU port's DMA engine,
  so the tag driver (``net/dsa/tag_rtl9602c.c``) moves no bytes. It has to
  exist all the same: the conduit hands the frames it receives to DSA only when
  its CPU port has a tag driver. The switch has a half of the mechanism too
  (see "The CPU tag, switch side").
- The conduit is the network interface ``cpu`` of the driver ``rtl9602c-eth``,
  which port 3 names in its ``ethernet`` property. The user ports appear on top
  of it as ``sfp@cpu`` and ``pon@cpu``. The conduit, the tag driver and the
  five calls that the switch driver makes into the conduit are described in
  Documentation/networking/device_drivers/ethernet/realtek/rtl9602c.rst.
- Every port is a fixed link. phylink does not learn a state from a PHY: it
  asks the driver for the state of each port, and the driver forces each MAC's
  link, speed and duplex, because no port has a partner to learn them from (see
  "Forced MAC ability" and "phylink and the lane parameters").

The driver implements 48 operations of ``struct dsa_switch_ops`` and the three
operations of ``struct phylink_mac_ops`` (``mac_config``, ``mac_link_up`` and
``mac_link_down``). The table groups the switch operations by the page that
describes what they do, named as in "Where to read next"; every operation name
is prefixed ``rtl9602c_``.

What the switch offloads
------------------------

Each item names the page that describes it.

- Bridging. A bridge of ``sfp`` and ``pon`` is forwarded by the switch: the
  address table, learning and its per-port limits, ageing, the flood flags of
  each port, port isolation, the spanning-tree state, VLAN filtering and
  membership, the S-VLAN and port mirroring (*bridging*). The GEM interfaces of
  the PON class are bridge ports too, and the switch forwards between them and
  the bridge's other ports itself.
- Filtering and quality of service. ``tc`` flower rules that drop, trap or
  pass and count become ACL rules, a rule that rewrites a C-VID a classifier
  entry, and a rule that polices broadcast, multicast or ARP by packet rate
  storm control; a matchall police is the port's ingress policer, ``tc`` tbf
  and ets set the egress shaper and scheduler of a port, and DCB sets the
  default priority, the DSCP map and the trust order of PCP and DSCP
  (*acl-qos*). The DoS checks, the storm-control classes that ``tc`` cannot
  describe, loop detection and the header-capture latch belong to the same
  page.
- Routing and NAT. The L3/NAT engine translates the source address and port of
  IPv4 TCP and UDP flows and forwards them, and their replies, without the CPU;
  its tables follow the kernel's address, neighbour and route notifiers, and
  each flow that netfilter's flowtable offload hands over gets its entries
  (*l3-nat*).
- Time. The switch's IEEE 1588 clock is a PTP hardware clock, and the PTP
  messages the switch sends to the CPU carry the time of the frame (*ptp*).
- The PON side. The GPON MAC and the PON MAC are driven through the PON class:
  the ONU's activation, the OMCI channel and a network interface for each GEM
  port (*PON* and *PON class*).

Device tree and binding
-----------------------

The ``switch`` node of ``arch/mips/boot/dts/realtek/rtl9602c.dtsi`` describes
the switch, and the board file ``dfp-34x-2c3.dts`` adds the two memory regions
of the PON MAC's packet buffer to it. The node, without the properties of the
ports::

    switch: switch@1b000000 {
            compatible = "realtek,rtl9602c-switch";
            reg = <0x1b000000 0xf10000>;
            interrupt-parent = <&intc>;
            interrupts = <8>;
            tx-disable-gpios = <&gpio0 13 GPIO_ACTIVE_HIGH>;
            realtek,sysctl = <&sysctl>;

            /* from dfp-34x-2c3.dts */
            memory-region = <&pbo_us>, <&pbo_ds>;
            memory-region-names = "pbo-us", "pbo-ds";

            ports {
                    #address-cells = <1>;
                    #size-cells = <0>;

                    port@0 { ... };
                    port@2 { ... };
                    port@3 { ... };
            };
    };

The binding is
``Documentation/devicetree/bindings/net/dsa/realtek,rtl9602c-switch.yaml``. It
takes ``dsa.yaml`` as its base, requires ``compatible`` (the constant
``realtek,rtl9602c-switch``), ``reg`` (one region) and ``interrupts`` (one
interrupt), and allows no property that neither it nor ``dsa.yaml`` names.
``memory-region`` needs ``realtek,sysctl`` and ``memory-region-names`` beside
it. DSA accepts the ports under ``ports`` as well as ``ethernet-ports``: the
tree uses ``ports``, the binding's example ``ethernet-ports``. The ports'
properties (``label``, ``phy-mode``, ``fixed-link``, ``ethernet``) are read by
DSA and phylink, not by the driver. The driver reads the other properties as
follows.

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Property
     - What the driver does with it
   * - ``reg``
     - Resource 0 is the register window, mapped once with
       ``devm_platform_ioremap_resource()`` (see "Access and
       identification").
   * - ``interrupts``
     - The output of the switch's interrupt block, which all of its sources
       share. It is source 8 of the SoC interrupt controller, Linux interrupt
       16, and is taken with ``platform_get_irq_optional()`` (see "The switch
       interrupt").
   * - ``tx-disable-gpios``
     - Optional. The hard transmit-disable input of the laser driver. Probe
       requests it with ``devm_gpiod_get_optional()`` as ``tx-disable``, already
       driven to its asserted level; without it every TX_DISABLE step is
       skipped. That GPIO 13, active high, is the laser driver's
       transmit-disable is not verified (*MIPS*).
   * - ``realtek,sysctl``
     - A phandle to the system controller, looked up with
       ``syscon_regmap_lookup_by_phandle()``. It holds the enable in front of
       the PON MAC (see "The system-controller enable in front of the PON
       packet buffer").
   * - ``memory-region``, ``memory-region-names``
     - The two DRAM areas of the packet buffer, found by the names ``pbo-us``
       and ``pbo-ds`` and each at least 1 MiB (``RTL9602C_PBO_DRAM``).

The board's device tree as a whole, including the fixed links of the three
ports, is described on the *MIPS* page.

Interfaces to user space
------------------------

- The network interfaces ``sfp`` and ``pon``. ``ip link set sfp up`` brings
  port 0 up, and the carrier of ``sfp`` follows the receiver of the SerDes lane
  (``/sys/class/net/sfp/carrier``, see "The SerDes lane to the host").
  ``ip link set pon up`` starts the ONU's activation, and fails if the driver
  refuses to start it, for instance when no serial number has been set. The CPU
  port has no user interface of its own; its conduit is the network interface
  ``cpu``.
- ``ip``, ``bridge``, ``tc`` and ``dcb`` for everything the switch offers to
  offload, and ``nft`` flowtables for routing and NAT; the pages listed under
  "What the switch offloads" describe what each command becomes in the
  hardware.
- ``ethtool -S sfp`` and ``ethtool -S pon`` list the 44 counters of the port,
  and ``ethtool -S sfp --groups eth-mac eth-ctrl rmon`` and ``ethtool -I -a
  sfp`` the standard statistics made from them; ``ip -s link show sfp`` counts
  what the port carried (see "Per-port counters"). The counters of the CPU
  port appear in the conduit's statistics under DSA's prefix ``s00_p03_``::

      ethtool -S cpu | grep s00_p03_

- ``devlink`` on the handle ``platform/1b000000.switch``: ``devlink dev info``,
  the 24 driver parameters (``devlink dev param``) and the region
  ``frame_capture`` (``devlink region``). ``devlink dev info`` also shows the
  identification of the part (see "Access and identification"); the rest is on
  the *devlink* page.
- The module parameters ``rtl9602c.sfp_mode`` and ``rtl9602c.sfp_an``, on the
  kernel command line and as read-only files in
  ``/sys/module/rtl9602c/parameters/`` (see "phylink and the lane parameters").
- ``/sys/kernel/debug/rtl9602c/``, one directory whose views the blocks of the
  driver create. ``rtl9602c-offload.c`` creates ``qdepth``, ``rma``, ``svlan``,
  ``hsd``, ``l3nat``, ``l3flow``, ``l2learn``, ``cf`` and ``l3capture``;

  ``gemusintr``, ``bwmap`` and ``uscntr``; ``rtl9602c-ponmac.c`` creates

      16: ...  rtl9602c-intc   8 rtl9602c-switch

How to read the fact tables
===========================

Each block below has a short account of what the hardware does and what the
driver does with it, followed by fact tables with three columns: *Fact*, *Tag*
and *Checked by*. The tag says how the fact is established. **M**, measured on
the board (the DFP-34X-2C3): *Checked by* gives the command or observation,
through the driver's own interfaces (the kernel log, ``ip``, ``ethtool``,
``devlink``, sysfs, debugfs), that shows it. **T**, tested by function: the
driver depends on the fact, and the named behaviour fails if it is wrong.
**P**, public standard: *Checked by* names the document and the clause. **I**,
inferred, not verified: the fact is an assumption, and *Checked by* says what
would confirm or refute it. The last chapter collects these facts and says
which of them the driver depends on.

A row with two tags is established in two ways, or in two parts; *Checked by*
says which part carries which tag. Register offsets are from the base of the
switch register window, physical ``0x1b000000``, unless a row says they are the
system controller's. Values are 32-bit words as ``readl()`` and ``writel()``
see them on this big-endian CPU. Port numbers are the hardware's, and "the
host" is the equipment at the far end of the SFP lane. The devlink handle of
the switch is ``platform/1b000000.switch``. The behaviours that a tested fact
depends on are named in words: the board boots to a shell; the SerDes link to
the host comes up, and recovers after host-side link bounces; bridged traffic
passes both ways, sourced from the host; VLAN filtering, FDB learning and
ageing work; the ACL hit counters, the policer and the storm-control rates
match their settings; the ONU reaches O5 on an OLT; OMCI messages pass both
ways over ``/dev/pon0omci0``; the optics diagnostics read, the laser is off
before O3 and TX_DISABLE is honoured.

Access and identification
=========================

The driver maps the switch's register window once and reaches every register
with a 32-bit read or write at a fixed offset. The part names itself in a model
register, which ``devlink dev info`` reads each time it is asked. Probe is
short: it finds what the PON MAC needs outside the switch, takes the laser's
TX_DISABLE line and registers the switch with DSA, whose call to setup does the
rest (see "Setup, in order").

Probe
-----

``rtl9602c_probe()``, in order:

1. Map the register window (resource 0 of the switch node). Purpose: every
   register access goes through it. (T)
2. Look up the system controller and the two packet-buffer regions
   (``rtl9602c_ponmac_probe()``; see "The system-controller enable in front of
   the PON packet buffer"). Purpose: the PON MAC needs them. A system
   controller that has not probed yet defers the probe; anything else missing
   only leaves the PON MAC unavailable. (T)
3. Request the optional ``tx-disable`` GPIO, already driven to its asserted
   level. Purpose: the laser emits nothing before the PON path enables it. (T)
4. Describe the switch to DSA (four ports, VLAN filtering switch-wide, the
   ageing range (*bridging*), the phylink MAC operations) and register it with
   ``dsa_register_switch()``. Purpose: DSA then calls
   ``rtl9602c_setup()``. (T)

All four steps are checked by the board booting to a shell with the switch
probed; steps 2 and 3 also by the laser being off before O3, with TX_DISABLE
honoured.

Forced MAC ability
==================

No port has a PHY, and nothing is negotiated on port 0's lane, so no MAC can
learn its link from a partner. The driver therefore forces the link, speed,
duplex and pause of every port it brings up, through two registers per port:
``RTL9602C_PORT_FORCE_VAL(p)`` holds the ability the MAC is told to use, and
``RTL9602C_PORT_FORCE_EN(p)`` says which forced values the MAC uses. Setup
forces the CPU port up, and phylink's link-up and link-down callbacks force
every port (``rtl9602c_force_link()``), the CPU port included. Port enable and
port disable change one bit of the enable word. 2.5 Gb/s is not among the
speeds a port can be forced to: port 0 at 2500BaseX runs as a 1000 Mb/s port
with a line-rate override.

The SerDes lane to the host
===========================

Port 0 has one SerDes lane, wired to the SFP edge connector. The host sees
carrier from this side's transmitter alone; the lane's own receiver has to
synchronise separately, and ``RTL9602C_SERDES_CTRL_LINK_UP`` says that it has.
The driver brings the lane up in a mode, 2500BaseX or 1000BaseX, with a fixed
sequence (``rtl9602c_serdes_init()``). The sequence runs at setup and again
when phylink asks for another mode, and it takes the link down. When the host
restarts its end, the lane is re-latched from phylink's link-down callback.

Bring-up
--------

The ten steps of ``rtl9602c_serdes_init()``, in order:

1. Set ``RTL9602C_SERDES_CTRL_CLK_STOP``. Purpose: stop the lane's clock before
   touching its analog settings. (T)
2. Clear ``RTL9602C_SERDES_CTRL_PCIE`` and set the mode to
   ``RTL9602C_SERDES_CTRL_MODE_OFF``. Purpose: park the lane. (T)
3. Write the seven analog words of ``RTL9602C_SERDES_ANA_BASEX_SEQ``, in the
   order of the table below. Purpose: the lane's analog settings, written while
   the lane is parked. (T)
4. In ``RTL9602C_SERDES_CTRL`` clear ``PCIE``, ``CLK_STOP`` and ``PHY_MODE``
   and set the requested mode. Purpose: restart the lane in that mode with its
   clock running. (T)
5. Clear ``RTL9602C_SERDES_FIBER_CTRL_PDOWN`` (bit 11 of
   ``RTL9602C_SERDES_FIBER_CTRL``, ``0x021c00``). Purpose: take the fibre PHY
   out of power-down. (T)
6. Set ``RTL9602C_PHY_CTRL_PATCH_DONE`` (bit 0 of ``RTL9602C_PHY_CTRL``,
   ``0x000110``). Purpose: set the patch-done flag of the fibre PHY. (T)
7. Write ``RTL9602C_SERDES_RESET`` (``0x021500``) three times with
   ``RTL9602C_SERDES_RESET_SEQ``: ``0x10``, ``0x30``, ``0x00``. Purpose: a reset
   pulse for the lane. (T)
8. Set or clear the 2.5G override for the mode: at 2500BaseX set
   ``RTL9602C_SHAPE_2G5_CFG_EN`` and write half the rate of port 0's shaper,
   ``RTL9602C_SHAPE_2G5_CFG_RATE_FULL`` when no tbf limits the port; in any
   other mode clear the enable only (see "Forced MAC ability"). Purpose: port 0
   carries 2.5 Gb/s as a 1000 Mb/s port with the override, and a tbf on it
   stays in force. (M)
9. Last, write ``RTL9602C_SERDES_AN_CTRL`` (``0x021808``) with
   ``RTL9602C_SERDES_AN_CTRL_INIT`` (``0x71e0``). Purpose: turn in-band
   auto-negotiation off on the SFP lane; without it the lane transmits and its
   receiver never synchronises. (M)
10. Remember the mode as the programmed one (``sds_mode``). Purpose: phylink's
    state and the check for a no-op ``mac_config`` read it. (T)

The steps tagged T are checked by the SerDes link to the host coming up: the
lane links about 20 ms after the sequence. Step 8 is checked as in "Forced MAC
ability". Step 9 is checked by the word ``RTL9602C_SERDES_AN_CTRL``, which read
``0x70e0`` on an unconfigured lane and ``0x71e0`` with a working link, the only
difference in the SerDes registers; with ``0x71e0`` written last,
``RTL9602C_SERDES_CTRL_LINK_UP`` rose and frames crossed. Whether steps 5 and 6
are needed is not known (see "Open questions").

Link-down resync
----------------

``rtl9602c_serdes_resync()`` runs from phylink's link-down callback on port 0,
where sleeping is allowed:

1. Save ``RTL9602C_SERDES_CTRL``. Purpose: the word to restore. (T)
2. Write it back with ``RTL9602C_SERDES_CTRL_CLK_STOP`` set. Purpose: stop the
   lane's clock. (T)
3. Write it with ``RTL9602C_SERDES_CTRL_PCIE`` clear and the mode
   ``RTL9602C_SERDES_CTRL_MODE_OFF``, the clock still stopped. Purpose: park the
   lane. (T)
4. Wait 20 ms. Purpose: let the parked lane settle. (T)
5. Write the saved word with ``RTL9602C_SERDES_CTRL_CLK_STOP`` clear. Purpose:
   restart the lane in its programmed mode with its clock running. (T)
6. Wait 50 ms. Purpose: give the lane time to settle. (T)

The steps are checked by the SerDes link to the host recovering after host-side
link bounces, 20 of 20 times, without rebooting the stick.

phylink and the lane parameters
===============================

All three ports are fixed links in the device tree, so phylink does not learn a
state from a PHY: it asks the driver for the state of each port once a second,
and at once when the interrupt reports a link change. The link of port 0 is the
receiver of its SerDes lane, not the carrier the host sees.

The lane runs as the host chooses, and nothing on it says which: a host port
that takes 2500BaseX sends it without in-band negotiation, and one that takes
only 1000BaseX commonly negotiates in band (IEEE 802.3 clause 37), and
sometimes does not. So the driver looks for the host's setting itself. Setup
brings the lane up in the first of three settings, 2500BaseX, then 1000BaseX
with in-band negotiation, then 1000BaseX without (``rtl9602c_sds_tries[]``),
and a work item, ``rtl9602c_sds_work()``, checks the lane once a second
(``RTL9602C_SDS_TRY_MS``), under ``sds_lock``:

1. The receiver has synchronised: keep the setting, logging ``SFP lane up in
   <setting>`` the first time. Purpose: a found setting stays. (M)
2. It has just lost the host: wait one more second in the same setting,
   logging ``SFP lane lost the host``. Purpose: a host restarting its end comes
   back in the setting it had. (M)
3. Otherwise bring the lane up in the next setting that may be tried. A setting
   with in-band negotiation clears the lane's FORCE bit after the bring-up,
   pulses its restart and re-latches the lane. Purpose: the host's setting is
   found within the three seconds the settings take. (M)

The module parameters ``sfp_mode`` and ``sfp_an`` narrow the settings tried.
phylink's ``mac_config`` leaves the lane alone: the interface it passes is the
device tree's ``phy-mode``, which says nothing about the host.

Maximum frame length
====================

The switch drops a frame longer than its frame length limit. The limit counts a
whole frame: header, VLAN tags, payload and FCS. The switch has two such
limits for all four ports, and a selector per port and speed class picks one.
The driver sets ``RTL9602C_FRAMELEN_LIMIT0`` to the largest MTU any port has
and ``RTL9602C_FRAMELEN_LIMIT1`` to the largest below it, each plus a fixed
overhead, and points each port at the lower limit that takes its MTU. The
overhead,
``RTL9602C_FRAME_OVERHEAD``, allows for two VLAN tags, a C-tag and an S-tag,
because translating between them is what the stick is for, and for the 8-byte
CPU tag, which the switch counts on a frame from the CPU port although the tag
travels in the DMA descriptor.

The switch interrupt
====================

The switch has an interrupt block of its own. Every source that is enabled
drives one output line into the SoC's interrupt controller: source 8, Linux
interrupt 16 (*MIPS*). ``RTL9602C_IRQ_ENABLE`` is the mask of the sources and
``RTL9602C_IRQ_PENDING`` shows which are pending. The driver requests the line
as a threaded interrupt named ``rtl9602c-switch``. The hard handler
``rtl9602c_irq()`` handles most of the sources itself and leaves the GPON
source to the thread ``rtl9602c_irq_thread()``.

Interrupt setup
---------------

``rtl9602c_irq_setup()``, from ``rtl9602c_setup()``, in order:

1. Write ``RTL9602C_IRQ_ENABLE`` = 0. Purpose: no source asserts the line while
   the handler is being put in place. (T)
2. Clear the event fields of ``RTL9602C_IRQ_LINK_STAT`` (a full chip reset left
   ``0x03080909`` there). Purpose: link events latched before the driver must
   not assert a line nobody handles. (T)
3. Request the line as a threaded interrupt with ``IRQF_ONESHOT``, named
   ``rtl9602c-switch``. Purpose: the handler exists before any source is
   unmasked. (T)
4. Register the teardown (``rtl9602c_irq_disable()``, run from devres).
   Purpose: mask every source and cancel the two work items before the line is
   freed. (T)
5. Enable LINK, METER and ACL. Purpose: link changes reach phylink at once, and
   policed drops and ACL hits are events. (T)
6. Subscribe the learning limit by rule (``rtl9602c_lrn_over_intr_sync()``).
   Purpose: the source is on only while a port has a limit somebody set. (T)

The mask goes up only after the handler exists, so that latched events from
before the driver cannot assert an unhandled line. With no interrupt in the
device tree, or if the request fails, the driver says so and leaves the link
state to phylink's once-a-second poll of the fixed links. The re-arm work and
the GPON worker are initialised at probe, whether there is an interrupt or
not, and the teardown cancels the GPON worker. Every change of
``RTL9602C_IRQ_ENABLE`` goes through ``rtl9602c_irq_enable()``, which holds a
spinlock for the read and the write: the interrupt handler, the re-arm work,
the learning-limit subscription, the ``loop_detect`` parameter, the PHC's
pulse-per-second request and the GPON bring-up all change it. The log line of a successful setup begins
``interrupt 16: link changes, policed drops and acl hits are events now`` and
ends with ``, and a deliberate learning limit`` when the learning limit is
subscribed. The steps are checked by the board booting to a shell and the
SerDes link recovering after host-side link bounces: at idle the count in
``/proc/interrupts`` does not move over 20 s, and a host bounce adds 2.

Per-port counters
=================

Each port has a receive block and a transmit block of counters in the switch's
register window, one 32-bit counter per word, read directly with no latch step.
The counters run free and wrap, so the driver keeps each as a 64-bit total
(``rtl9602c_mib_fold()``): every read adds the difference since the last one,
modulo 2^32, and a worker folds every port every ``RTL9602C_MIB_FOLD_S`` (60)
seconds, within the 19 minutes a counter takes to wrap at the SFP port's 2.5
Gb/s of frames of minimum size. The same worker folds the ACL's log counters
(*acl-qos*, "Hit counts"). ``rtl9602c_get_ethtool_stats()`` reports all
44 totals of a port on every ``ethtool -S``, under the names of the tables
below; DSA lists its own ``tx_packets``, ``tx_bytes``, ``rx_packets`` and
``rx_bytes`` before them. The two octet counters are 64 bits wide: the driver
reads the high word, the low word and the high word again, and repeats while
the high word moved, so that a carry between the reads cannot corrupt the
value. ``rx_forward_discards`` is in the transmit block but counts frames
received on the port and discarded by forwarding. The *Tag* column of the
tables says how the offset is established, by the rows that follow them.

The same totals make the standard statistics. ``get_stats64`` gives the
interface statistics that ``ip -s link`` shows, which therefore count what the
port carried, bridged traffic included, and not only what crossed the CPU:
packets are the unicast, multicast and broadcast frames together; receive
errors the CRC and alignment errors, the symbol errors, and as length errors
the undersize, oversize, fragment and jabber frames; receive drops the port's
drop events and the forwarding discards; transmit drops ``tx_discards``;
collisions ``tx_collisions``, with the excessive and the late ones as transmit
errors. ``get_eth_mac_stats``, ``get_eth_ctrl_stats``, ``get_rmon_stats`` and
``get_pause_stats`` fill the IEEE 802.3 and RMON groups of ``ethtool -S
--groups`` and the pause statistics of ``ethtool -I -a``, the RMON size buckets
being 64 to 1518 bytes in the six ranges of the counters and 1519 to 16383.

Restart, reload and teardown
============================

A warm restart of the CPU does not reset the switch, and a module reload leaves
it running with its registers and tables as they were. Only a full chip reset,
the reset the watchdog performs (*MIPS*), starts it over. The driver therefore
writes every piece of state it depends on at setup rather than assuming reset
values, and it does not rely on what the boot loader leaves, which depends on
the boot loader's environment.

Teardown
--------

``rtl9602c_remove()`` calls ``dsa_unregister_switch()``, and DSA calls
``rtl9602c_teardown()``, which undoes setup in this order:

1. Cancel the GPON work and the counter fold. Purpose: on a board without the
   interrupt nothing else cancels the GPON work, and neither must run while the
   parts they use go. (T)
2. Unregister the L3 notifiers (address, neighbour and route). Purpose: they can
   run on any CPU and touch the tables, so they go before anything they touch.
   (T)
3. Stop the L3/NAT engine: trap this device's own addresses to the CPU again,
   clear the engine's master enable and empty its tables (*l3-nat*). Purpose: no
   flow is forwarded by rows that no driver keeps. (T)
4. Tear down the GEM data path. Purpose: the PON device is unregistered with
   its last child, the OMCI port, and the data path must not outlive it. (T)
5. Tear down the OMCI channel. (T)
6. Remove the debugfs directory ``rtl9602c``. (T)
7. Unregister the PHC. (T)
8. Destroy the ``frame_capture`` region and, if setup registered them, the
   devlink parameters. Purpose: they go before the devlink instance does, so
   that the next probe does not find their names taken; parameters that were
   never registered are not unregistered. (T)

The interrupt is undone last, by devres, after ``rtl9602c_remove()`` has
returned: ``rtl9602c_irq_disable()`` writes ``RTL9602C_IRQ_ENABLE`` = 0, then
cancels the re-arm work and the GPON worker. The steps are checked by a module
reload: after ``rmmod`` and ``insmod``, the parameters are there again.

Setup, in order
===============

DSA calls ``rtl9602c_setup()`` once the switch is registered. Everything the
driver depends on is written here, because a warm restart or a reload leaves
the switch as it was (see "Restart, reload and teardown"). The SerDes lane comes
first, since nothing reaches the host without it. From the GPON report on, a
part that fails is logged and setup still succeeds: a switch without its
optics, its PHC, its OMCI channel or its GEM data path still switches frames.
A step that belongs to another page is named and handed over.

1. Bring up the SerDes lane in the first setting that ``sfp_mode`` and
   ``sfp_an`` leave, and start the work that looks for the host's setting (see
   "The SerDes lane to the host" and "phylink and the lane parameters"; the log
   line is ``SFP lane in 2500BaseX, looking for the host's setting``). Purpose:
   the lane first, because nothing else carries a frame without it. (T)
2. Force the CPU port up at 1000 Mb/s full duplex (see "Forced MAC ability").
   Purpose: the CPU port comes out of reset with its forced link clear. (T)
3. Set both CPU tag directions in ``RTL9602C_CPUTAG_CTRL`` (see "The CPU tag,
   switch side"). Purpose: the source port, the reason and the PON flow reach
   the receive descriptor, and the switch reads the tag of frames from the CPU.
   (T)
4. Turn the address table's CAM on, then empty the L2 table, the CAM included,
   and the NAT tables (*bridging*, *l3-nat*). Purpose: they survive a warm
   restart. (T)
5. Run the indirect table self-test (*bridging*). Purpose: check that the
   table engine reaches the VLAN entries where the driver expects them. A
   failure is logged and setup continues. (T)
6. Set up the interrupt (see "Interrupt setup"). (T)
7. Mark the DSCP map switch-wide, forget the apptrust owner and read the
   classifier depth (*acl-qos*). (T)
8. Report the memory self-test (see "Access and identification"). (T)
9. Switch the DoS checks off, with the flood thresholds at 0 in the registers
   and in the driver's copy (*acl-qos*). Purpose: no check enabled before the
   driver loaded survives. (T)
10. Switch storm control off, free the meters and clear their latches
    (*acl-qos*). Purpose: a latch left from before would read as a policed drop
    that never happened. (T)
11. Write the ACL, the classifier, the priority maps, the PCP remark, the
    policer, the scheduler and the shaper as a full chip reset leaves them
    (*acl-qos*).
    Purpose: no rule, entry or limit that an earlier kernel wrote stays in
    force with no record of it in the driver. (M)
12. Limit the frames that the CPU port's queues 0 to 6 hand the CPU to 5000 a
    second (*acl-qos*). Purpose: the switch drops a flood to the CPU before it
    takes the CPU's time. (M)
13. Write the mirror word 0 (*bridging*). Purpose: a mirror that an earlier
    kernel set would survive a warm restart. (M)
14. Recognise S-tags on the SFP and PON ports and let every other frame pass as
    it came (``rtl9602c_svlan_setup()``, *bridging*). Purpose: the VLAN rules
    of tc flower can match and pop S-tags. (M)
15. Write the two L4-port field selectors (*acl-qos*). (T)
16. With bridge multicast snooping in the kernel, add the ACL rules that copy
    IGMP and MLD from the SFP and PON ports to the CPU
    (``rtl9602c_acl_snoop_setup()``, *acl-qos*). Purpose: the bridge snoops
    the reports to groups already in the table, which the switch would
    otherwise send only to the group's members. (M)
17. Set the reserved-address exemptions from storm control (*acl-qos*). (T)
18. Switch loop detection off and clear its latches (*acl-qos*). Purpose: a
    loaded driver must not start sending probes onto a network by itself. (T)
19. Arm the header capture in mode none (*acl-qos*). Purpose: no capture
    predates the driver. (T)
20. Register the devlink parameters and the region (*devlink*). A failure is
    logged and the switch carries on. (T)
21. Set standalone forwarding: each port's flood request is set to what reset
    leaves (unknown unicast, unknown multicast and broadcast flooding), the GEM
    bridge state is cleared, unregistered multicast is flooded as after a
    reset (``rtl9602c_mcast_reset()``), and the bridge refresh writes
    isolation, flooding and learning from that state (*bridging*, *PON*). (T)
22. Bring up the L3/NAT engine and register its notifiers (*l3-nat*). (T)
23. The GPON report (*PON*), the debugfs views, the I2C master and the optics
    hwmon device (*PON*), the PHC (*ptp*), the OMCI channel and the GEM data
    path (*PON*). A failure in any of these is logged and setup still succeeds.
    (T)
24. Start the counter fold (see "Per-port counters"). Purpose: no counter wraps
    between two folds. (T)

The steps are checked as follows. Step 1 by the SerDes link to the host coming
up. Steps 2 and 3 by bridged traffic passing both ways, sourced from the host.
Steps 4 and 5 by VLAN filtering, FDB learning and ageing working, and by the
board booting to a shell. Steps 6 to 8 by the board booting to a shell and the
SerDes link recovering after host-side link bounces. Steps 9, 10, 15 and 17 to
19 by the ACL hit counters, the policer and the storm-control rates matching
their settings, and by the board booting to a shell; step 11 by the ``qos`` and
``cf`` views after a warm reboot, step 12 by the CPU's share of a flood, and
step 16 by the bridge's group timers restarting on reports (*acl-qos*). Step 13
by the mirror word read after a warm restart, and step 14 by S-tags pushed,
matched and popped (*bridging*). Steps 20 to 22 by bridged traffic passing both
ways, VLAN filtering and FDB learning working, and a routing and NAT test that
sees a translated source address on the wire. Step 23 by the board booting to a
shell, the PTP hardware clock reading and steering, OMCI passing both ways over
``/dev/pon0omci0`` and the optics diagnostics reading. Step 24 by the interface
statistics, which count what the ports carried.

The system-controller enable in front of the PON packet buffer
==============================================================

``0xf00000``, sit behind an enable in the system controller. Until

driver reaches the system controller as a syscon regmap and sets the bit when
the PON MAC is first built, at the first bring-up of the PON and before the
first access; it reads nothing in the block before that, and it never clears

Known limitations
=================

- The largest MTU a user port takes is the conduit's, 1508, room for PPPoE's
  1500-byte packets (RFC 4638). ``rtl9602c_port_max_mtu()`` reports 16349, but
  DSA bounds the MTU of a user port by the ``max_mtu`` of the conduit, so a
  larger MTU on ``sfp`` or ``pon`` fails with ``-ERANGE``: the conduit's
  transmit engine, in the mode the driver uses, stops on long frames (see the
  *CPU port* page). The switch's own limit, described in "Maximum frame
  length", is not what stops it.
- The switch has two frame length limits for four ports, so with three
  different MTUs a port with the smallest accepts frames up to the middle one's
  limit (see "Maximum frame length").
- Pause on the SerDes port is set only by the device tree: the ports are fixed
  links, so ``ethtool -A sfp`` fails with ``EOPNOTSUPP``, and the board's
  device tree leaves pause off. Pause also does not keep a flood to the CPU
  from being dropped, since the switch drops it at the CPU port's queue
  without sending pause frames.
- The lane finds a host's setting by trying three in turn, a second each, so it
  takes up to three seconds after the host has changed or come back, and while
  no host is there the lane changes setting every second. Of the three,
  1000BaseX without in-band negotiation has not been seen to link: the bench
  host cannot run it.
