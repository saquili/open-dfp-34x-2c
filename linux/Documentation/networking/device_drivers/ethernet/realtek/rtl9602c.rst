===============================================
Realtek RTL9602C CPU port driver (rtl9602c-eth)
===============================================

Overview
========

The Ethernet switch of the RTL9602C has four ports. Port 0 is the SerDes lane
to the host, port 1 exists in the silicon and is not wired on this board, port
2 is the PON port, behind which the GPON MAC sits, and port 3 is the CPU port.
The CPU port has no MAC behind it: it ends in a DMA engine that moves frames
between memory and the switch through descriptor rings: one for transmit, and
two for receive, the data ring and the control ring, which takes the OMCI
messages.

Everything that decides where a frame goes travels in the descriptors, as the
CPU tag, and none of it is in the frame. On transmit the descriptor carries a
destination port mask, a priority and a PON flow. On receive it carries the
source port, the reason the switch sent the frame up and the PON flow the frame
arrived on. The tag has two halves: the descriptor fields, which this driver
fills in and reads, and two controls in the switch, which the switch driver
sets (see "The CPU tag, switch side").

The driver, ``rtl9602c-eth``, is the conduit of the switch driver in the sense
of DSA: the network interface that connects the CPU to the switch. It is named
``cpu``, and the switch's user ports appear on top of it as ``sfp@cpu`` and
``pon@cpu``. The DSA tag driver, ``rtl9602c``, moves no bytes, because the tag
is not in the frame: on transmit it records the destination port for the
conduit, and on receive the conduit tells DSA which port a frame came from
without calling it. Besides ordinary frames the conduit:

- carries the OMCI channel of the PON port: the switch driver sends OMCI
  messages through the conduit and receives them from it;
- carries the frames of the GEM ports: a frame of a GEM interface reaches the
  conduit directly and leaves in the PON flow it names, and a frame that
  arrives in a PON flow is offered to the switch driver first;
- takes off the timestamp tag that the switch inserts into the PTP messages it
  sends to the CPU, keeping its time as the frame's hardware timestamp;
- counts frames, and the frames the switch sent up per reason.

The path of a frame, from the users of the conduit down to the switch::

    sfp@cpu   pon@cpu        GEM interfaces          OMCI port
       |         |                 |                     |
    +--+---------+--+              |                     |
    |   tag driver  |              |                     |
    +-------+-------+              |                     |
            |                      |                     |
            +----------------------+---------------------+
                                   |
                     cpu (rtl9602c-eth), the conduit
                                   |
             three descriptor rings, the CPU tag in the descriptors
                                   |
                 DMA engine = CPU port = switch port 3
                                   |
                 +-----------------+-----------------+
                 |                                   |
          port 0: SerDes lane                 port 2: PON port
          to the host                         (GPON MAC)

``sfp@cpu`` and ``pon@cpu`` are user ports of DSA, and the tag driver records
the destination port of their frames. A frame of a GEM interface and an OMCI
message reach the conduit without it: the GEM interfaces and the OMCI port
belong to the PON class (Documentation/networking/pon.rst), which the switch
driver feeds through the conduit. The switch itself is described in
Documentation/networking/dsa/rtl9602c.rst, and the GPON MAC and the PON MAC in
Documentation/networking/device_drivers/pon/rtl9602c.rst.

Device tree and binding
-----------------------

The ``eth`` node of ``arch/mips/boot/dts/realtek/rtl9602c.dtsi`` describes the
engine, and the CPU port of the switch (``port@3``) refers to it through its
``ethernet`` property::

    eth: ethernet@18012000 {
            compatible = "realtek,rtl9602c-eth";
            reg = <0x18012000 0x1440>;
            interrupt-parent = <&intc>;
            interrupts = <26>;
    };

    port@3 {
            reg = <3>;
            ethernet = <&eth>;
            phy-mode = "internal";

            fixed-link {
                    speed = <1000>;
                    full-duplex;
            };
    };

The binding is
``Documentation/devicetree/bindings/net/realtek,rtl9602c-eth.yaml``. It
requires ``compatible`` (the constant ``realtek,rtl9602c-eth``), ``reg`` (one
region) and ``interrupts`` (one interrupt), allows no other property and
expects the node name ``ethernet@<address>``. The unit's MAC address is not a
device tree property: the boot loader leaves it in the engine's address
registers, and the driver adopts it (see "Registers"). The driver maps the
region with ``devm_platform_ioremap_resource()`` and takes the interrupt with
``platform_get_irq()``.

Interfaces to user space
------------------------

- The network interface ``cpu``. ``ip -s link show cpu`` shows its counters
  (see "Statistics"). Its address is the one the boot loader left in the
  engine, or a random one when that is not a usable unicast address;
  ``ip link set cpu address`` changes the interface's address only, because the
  driver never writes the engine's address registers and the engine accepts
  every frame. It has four transmit queues, one per switch port, and one
  receive queue. ``ip link set cpu down`` halts the engine and setting it up
  again restarts it (see "Sequences").
- The user ports ``sfp@cpu`` and ``pon@cpu``. The ``SO_PRIORITY`` of a frame
  sent on ``sfp`` chooses its egress queue at the switch, and the receive time
  of a PTP message on ``sfp`` arrives as the frame's hardware timestamp (see
  "Transmit" and "The timestamp tag on PTP frames").
- ``ethtool -S cpu``. The conduit has no ``ethtool`` operations of its own, and
  the driver no module parameters; DSA adds the switch's counters for the CPU
  port under the prefix ``s00_p03_``
  (Documentation/networking/dsa/rtl9602c.rst).
- ``/sys/kernel/debug/rtl9602c-eth/rxreason``: the frames the switch sent up,
  counted per reason. Reading it lists the non-zero counts and any write
  clears them (see "Statistics").
- ``/sys/kernel/debug/rtl9602c-eth/rings``: the priority-to-ring map, and per
  receive ring its length, the engine's index into it, the driver's, and the
  frames taken from it since the interface came up (see "The rings").
- ``/proc/interrupts``: the engine's interrupt, source 26 of the SoC interrupt
  controller, is Linux interrupt 34 and is named after the interface::

    34: ...  rtl9602c-intc  26 cpu

- The kernel log lines that begin with ``rtl9602c-eth`` and the interface name
  (see "Logging").
- Through the switch driver, the OMCI port ``/dev/pon0omci0`` and the GEM
  interfaces of the PON class (Documentation/networking/pon.rst) send and
  receive their frames through the conduit.

How to read the fact tables
===========================

Each block below has a short account of what the hardware does and what the
driver does with it, followed by fact tables with three columns: *Fact*, *Tag*
and *Checked by*. The tag says how the fact is established. **M**, measured on
the board (the DFP-34X-2C3): *Checked by* gives the command or observation,
through the driver's own interfaces (the kernel log, ``ip``, ``ethtool``,
debugfs), that shows it. **T**, tested by function: the driver depends on the
fact, and the named behaviour fails if it is wrong. **P**, public standard:
*Checked by* names the document and the clause. **I**, inferred, not verified:
the fact is an assumption, and *Checked by* says what would confirm or refute
it. The last chapter collects these facts and says which of them the driver
depends on.

A row with two tags is established in two ways, or in two parts; *Checked by*
says which part carries which tag. "Every boot" means that the line is in the
kernel log of every boot of this kernel. Register offsets are from the base of
the engine's window, physical ``0x18012000``. The words of a descriptor are
numbered from 0, and a range of bits such as 28:23 runs from the high bit to the
low one. The behaviours that a tested fact depends on are named in words: the
board boots to a shell; bridged traffic passes both ways, sourced from the
host; OMCI messages pass both ways over ``/dev/pon0omci0``.

The engine
==========

The engine has a register window of its own in the SoC's peripheral area, apart
from the switch's registers. The registers are big-endian, and on this
big-endian CPU ``readl()`` and ``writel()`` access them in native order; the
byte and half-word registers are accessed at their own width. After a cold start
the boot loader leaves the engine idle, and it leaves the unit's MAC address in
the engine's address registers. If the boot loader has used the engine to
receive an image over the network, it leaves the engine enabled, and the probe
stops it first (see "Setting the engine up"). The engine's interrupt is source
26 of the SoC interrupt controller, which is Linux interrupt 34
(Documentation/arch/mips/rtl9602c.rst).

Address and receive filtering
-----------------------------

The boot loader leaves the unit's MAC address in the engine's address
registers, and the driver adopts it as the address of ``cpu``. The engine
accepts every frame the switch hands it and does not filter again: the switch
decides what reaches the CPU. The receive format is written rather than
inherited, so that it does not depend on what the boot loader left.

.. list-table::
   :header-rows: 1
   :widths: 58 6 36

   * - Fact
     - Tag
     - Checked by
   * - ``RTL9602C_NIC_MAC_ADDR_HI`` (``+0x0000``, 32-bit) holds MAC address
       bytes 0 to 3, byte 0 in bits 31:24; ``RTL9602C_NIC_MAC_ADDR_LO``
       (``+0x0004``) holds bytes 4 and 5 in bits 31:16, and bits 15:0 read 0.
       The boot loader leaves the unit's address there. The driver adopts it
       and never writes these registers; if they do not hold a valid unicast
       address it says so and uses a random one.
     - M
     - The same address is read at the boot loader prompt and printed by the
       probe line.
   * - ``RTL9602C_NIC_RX_FILTER`` (``+0x0044``) is written with
       ``RTL9602C_NIC_RX_FILTER_PROMISC`` (``0x0000000f``): the engine accepts
       every frame the switch hands it, whatever the destination address. The
       switch decides what reaches the CPU; the engine does not filter again.
     - T
     - Frames addressed to other hosts cross the CPU when it bridges them;
       broadcast (ARP) and the board's own unicast frames arrive (ssh to the
       board works).
   * - ``RTL9602C_NIC_MC_HASH_LO`` and ``RTL9602C_NIC_MC_HASH_HI`` (``+0x0008``,
       ``+0x000c``) form a 64-bit multicast hash filter; the driver writes all
       ones to both so that no multicast group is filtered.
     - T
     - Multicast reaches the CPU: PTP Sync frames to ``01:1b:19:00:00:00`` are
       received and timestamped (also measured on the DFP-34X-2C3); IPv6
       neighbour discovery works.
   * - ``RTL9602C_NIC_CTRL`` (``+0x003b``, 8-bit) is written with
       ``RTL9602C_NIC_CTRL_INIT``, ``RTL9602C_NIC_CTRL_RX_CSUM`` (bit 1) and
       ``RTL9602C_NIC_CTRL_RX_JUMBO`` (bit 3) together: ``0x0a``. Bit 2 stays
       clear, and with it clear a received frame keeps its 802.1Q tag in the
       frame. The register is written rather than inherited, so that the
       receive format does not depend on what the boot loader left.
     - T
     - VLAN-tagged frames of the management VLAN arrive whole: ssh over the
       management VLAN works, and so does a long reply over it.
   * - With ``RTL9602C_NIC_CTRL_RX_JUMBO`` set, a 1522-byte VLAN-tagged frame (a
       full 1500-byte payload) is received. That bit 3 is what admits frames
       above 1518 bytes is an assumption: it was never tested with the bit
       clear.
     - M, I
     - M: 1500-byte pings over a VLAN, every request counted by the board's own
       ICMP statistics. I: clearing the bit and repeating the pings would
       settle it.

Transmit configuration and the CPU tag registers
------------------------------------------------

``RTL9602C_NIC_CPUTAG`` switches the CPU tag on in the descriptors. With it,
and with the switch's own controls (see "The CPU tag, switch side"), the switch
obeys the port mask of transmit word 3 and fills receive words 2 and 3.
``RTL9602C_NIC_CPUTAG_SRC`` takes a second value whose fields are not
established. The driver writes these two registers, and ``RTL9602C_NIC_TX_CFG``,
as whole values.

   :header-rows: 1
   :widths: 58 6 36

       is taken to set an inter-packet gap of 3 (bits 11:10) with loopback off

Priority steering and the missed-frame counter
----------------------------------------------

One register of the engine has a field per internal priority that names the
receive ring for that priority. The driver serves two rings and sends priority
7, which the switch driver gives the OMCI messages it traps, to the control
ring, and every other priority to the data ring (see "The rings"). Frames the
engine drops because no receive descriptor is free are counted in a 16-bit

Interrupts and the poll
=======================

The engine has one interrupt line, source 26 of the SoC interrupt controller,
Linux interrupt 34. ``RTL9602C_NIC_IRQ_STAT`` shows what is pending and
``RTL9602C_NIC_IRQ_MASK`` selects what may raise the line; the two share one
bit layout. The handler ``rtl9602c_eth_irq()`` reads the status: zero means the
interrupt is not the engine's. Otherwise it writes the status back to
acknowledge it, writes 0 to the mask and schedules the NAPI poll. The poll,
``rtl9602c_eth_poll()``, folds in the missed-frame count, reaps transmit
completions and receives up to its budget; when it finishes under the budget it
writes ``RTL9602C_NIC_IRQ_MASK_RXTX`` to the mask again. Every status bit is
handled alike, whatever raised it, so the meaning of the individual bits
carries no weight (see "The interrupt and the poll" under "Sequences").

The rings
=========

The engine has one transmit ring and, as the driver uses it, two receive rings:
the data ring, at ``RTL9602C_NIC_RX_RING_BASE``, and the control ring, at
``RTL9602C_NIC_RX2_RING_BASE``, which takes the frames of internal priority 7
(see "Priority steering and the missed-frame counter"). Each ring is an array
of descriptors in coherent memory (see "Descriptors"). The driver gives the
engine the bus address of descriptor 0 of each ring, and the engine walks a
ring by an index of its own, returning to descriptor 0 after the descriptor
marked ``RTL9602C_NIC_DESC_RING_END``. The two sides pass a descriptor to each
other with the ownership bit of word 0: set, the descriptor is the engine's.
The engine learns that the transmit ring has work from a kick, a write to
``RTL9602C_NIC_DMA_CTRL`` with the poll bit set. Each receive ring has a tail
register that holds the index of the last descriptor handed back to the engine,
and the driver writes it each time it gives a descriptor back.

The control ring exists so that OMCI keeps free descriptors whatever the data
ring holds: under a flood to the CPU the data ring is full nearly all the time
and the engine drops what arrives for it, while the control ring, which nothing
else fills, still takes every OMCI message. The poll serves the control ring
first, so a full budget of data cannot hold a message back. The rings file
in debugfs shows both rings::

    # cat /sys/kernel/debug/rtl9602c-eth/rings
    priority to ring 20000000
    data    ring 256 descriptors, engine at  89, driver at  89, 89 frames
    control ring  32 descriptors, engine at   5, driver at   5, 421 frames

Descriptors
===========

A descriptor is an array of big-endian 32-bit words in coherent memory
(``dma_alloc_coherent()``): uncached on this CPU, which is not cache-coherent
with DMA, so the driver and the engine see each other's stores without cache
maintenance. A transmit descriptor has five words (``struct rtl9602c_tx_desc``:
``stslen``, ``addr``, ``tag``, ``dest``, ``lso``) and a receive descriptor four
(``struct rtl9602c_rx_desc``: the first four). Word 0 holds the ownership and
control bits and the length, word 1 the bus address of the buffer, and words 2
and 3 the CPU tag; word 4, transmit only, is large-send offload and is always
0. The tables give the fields by word; the rows that follow say what the
driver does with them.

Transmit
--------

For each frame the driver builds the descriptor from the frame and its queue.
The switch port comes from the transmit queue, which the tag driver chose (see
"The conduit and DSA"); the priority from ``skb->priority``, and the PON flow
from a ``METADATA_HW_PORT_MUX`` dst that a GEM interface's frame carries. The
driver pads a frame shorter than 60 bytes, has the engine append the FCS, and
always names exactly one destination port. An OMCI message is sent differently
from a data frame (see "The OMCI channel").

Receive
-------

The driver hands each receive descriptor to the engine with a buffer size of
1536 bytes (``RTL9602C_RX_BUF``) and allocates 64 bytes more
(``RTL9602C_RX_SLACK``). The engine writes a received frame from 2 bytes into
the buffer (``RTL9602C_NIC_RX_DATA_OFFSET``), and the length in word 0 counts
the frame with its FCS but not those 2 bytes. Words 2 and 3 are written only
for a frame the switch attached a CPU tag to. The driver reads them once, after
the engine has released the descriptor, and clears them when it gives the
descriptor back. A frame longer than its buffer comes in several descriptors,
and the driver copies the pieces into one buffer. A frame marked as an OMCI
message has no Ethernet header (see "The OMCI channel").

       (``0x600``, 1536) in its length field, the buffer size it advertises, and
       allocates ``RTL9602C_RX_BUF`` + ``RTL9602C_RX_SLACK`` (64) bytes
       (``RTL9602C_RX_ALLOC``), so a frame of the advertised length written 2
       bytes in still ends inside the buffer. That the engine writes that far
       is not established; the margin makes the question harmless.

The CPU tag, switch side
========================

The CPU tag is one mechanism with two halves. The engine's half is in the
descriptors (see "Descriptors"). The switch's half is one register of the
switch, ``RTL9602C_CPUTAG_CTRL``, which the switch driver writes in its setup
by read-modify-write: ``RTL9602C_CPUTAG_CTRL_INSERT`` makes the switch attach a
tag to every frame it sends to the CPU port, which is what fills receive words
2 and 3, and ``RTL9602C_CPUTAG_CTRL_PARSE`` makes it read the tag of the frames
from the CPU. The switch's frame-length check counts the CPU tag on a frame
entering from the CPU port, although the tag is not in the frame, and the
switch driver allows for it in the limit it programs
(Documentation/networking/dsa/rtl9602c.rst).

The timestamp tag on PTP frames
===============================

The switch writes the receive time of a PTP message into the frame itself. This
is separate from the CPU tag: the timestamp tag is in the frame, the CPU tag in
the descriptor. The switch inserts 16 bytes into a well-formed PTP message that
it sends to the CPU port, between the source address and the message's own
EtherType, and the tag opens with EtherType ``0x8899``. The conduit takes the
tag off before DSA or a PTP stack sees the frame: it keeps the time as the
frame's hardware timestamp (``skb_hwtstamps()``), moves the two addresses
forward by 16 bytes and pulls the tag, so that the frame reaches the stack as
it was sent. The tag carries only the low 16 bits of the seconds of the
switch's PTP clock; the switch driver completes them from the clock
(``rtl9602c_port_rxtstamp()``, Documentation/networking/dsa/rtl9602c.rst).

     - The kernel log with the switch's ingress action for Sync at "none" (240)
       and at "mirror" (241).
   * - A frame with a tag comes up with the same reason in its receive
       descriptor, ``RTL9602C_RX_REASON_PTP`` (240) for a message sent to the
       CPU, and the driver takes a tag off only a frame with a CPU tag and
       that reason or ``RTL9602C_RX_REASON_PTP_MIRROR`` (241). A frame that
       only looks tagged, which a host can send, comes up with the reason of
       an ordinary frame and goes up as it came.
     - M, I
     - M: the ``rxreason`` view counted 100 frames at reason 240 for 100 Syncs
       from the host, and 100 at reason 0 for 100 frames shaped like a tag
       from the host; with the check, the second kind reached a packet socket
       whole, without a hardware stamp. I: the descriptor's reason for a
       mirrored copy, taken to be 241 like its tag.
   * - Offsets 22 and 23 (``RTL9602C_PTP_TAG_SEC_OFFSET``) are the low 16 bits
       of the seconds of the switch's PTP clock at the moment the switch
       stamped the frame; offsets 24 to 27 (``RTL9602C_PTP_TAG_NSEC_OFFSET``)
       the nanoseconds, 32 bits, big-endian, counted in nanoseconds. The
       conduit stores the two as the frame's hardware timestamp; the switch
       driver fills in the upper seconds from its clock.
     - M
     - The seconds tracked the PTP clock read alongside; frames sent 250 ms
       apart were stamped 250.221 and 250.177 ms apart, frames 200 ms apart
       200,209,520 and 200,212,192 ns apart, read through ``SO_TIMESTAMPING``
       on the switch port.
   * - Offsets 16 to 21 are not read (one dump read ``00 08 00 00 00 00``).
       Whether offsets 18 to 21 carry higher bits of the seconds is not
       established, nor whether the stamp is taken when the frame enters the
       switch or when it leaves toward the CPU.
     - I
     - Not load-bearing for this driver: the upper seconds come from the clock,
       and the stamp is passed on as it is. Reading the bytes with the clock set
       past 65,536 s would settle the first question.
   * - The insertion does not depend on the port's PTP enable nor on the ingress
       action, and the EtherType alone does not cause it: bare frames with
       EtherType ``0x88f7``, ``0x88f8`` or ``0x0800`` and a zero body arrive
       untagged.
     - M
     - Frames were tagged with the port's PTP enable on and off and under every
       ingress action; the three bare frames arrived at 60 bytes.
   * - The conduit takes the tag off: when a frame longer than 16 bytes has
       EtherType ``0x8899`` at offset 12, it records the timestamp, moves the
       two addresses forward by 16 bytes and pulls the tag, so the frame reaches
       the stack as it was sent. It must: a PTP message over Ethernet is
       recognised by EtherType ``0x88F7``, which neither the DSA core's PTP
       classification nor any PTP stack would find behind the tag.
     - M
     - The Sync reaches user space as 60 bytes with EtherType ``0x88f7``, three
       frames of three. PTP over Ethernet: IEEE 1588-2008, Annex F.
   * - Other frames than PTP-tagged ones carry EtherType ``0x8899`` at offset
       12: the switch's loop-detection probes do (captured at the far end).
       The conduit tells a timestamp tag by the protocol byte at offset 14, 4,
       and leaves any other ``0x8899`` frame whole.
     - I
     - Sending a ``0x8899`` frame with a protocol byte other than 4 to the
       board's address and checking that it arrives whole would settle it.

The conduit and DSA
===================

DSA reaches the CPU port through its conduit, and a DSA switch normally has a
tag in every frame: the tag driver adds it on transmit and removes it on
receive. Here the CPU tag is in the descriptors, so the tag driver has no bytes
to move and the work is split between it and the conduit as follows.

.. list-table::
   :header-rows: 1
   :widths: 14 43 43

   * - Direction
     - Tag driver (``net/dsa/tag_rtl9602c.c``)
     - Conduit (``rtl9602c-eth.c``)
   * - Transmit
     - Records the destination port of the user port in the frame's queue
       mapping and returns the frame unchanged. Drops a frame sent on the
       ``pon`` interface.
     - Turns the queue into the port mask of descriptor word 3, and adds the
       priority (word 2) and, for a GEM frame, the flow.
   * - Receive
     - Its callback drops every frame it is called with.
     - Attaches to each tagged frame a dst that names the source port, so that
       DSA delivers the frame on that user port without calling the tag
       driver.

``-EINVAL``, if it is not. There is one OMCI handler and one data-frame handler
at a time.

The OMCI channel
================

OMCI messages (ITU-T G.988) cross the PON port in the flow of the OMCC, the
ONU's OMCI channel. Downstream, the PON MAC hands the message to the switch,
which traps it to the CPU port and marks it in the receive descriptor
(``RTL9602C_NIC_RXD_OMCI``); the conduit offers it, with its source port, to the
switch driver's OMCI handler. A message has no Ethernet header. Upstream, the
switch driver's OMCI port passes the message to
``rtl9602c_conduit_ctrl_xmit()`` with the PON port and the OMCC's flow. The
message shares the transmit ring with data frames, leaves at the length given
(a 48-byte baseline message is not padded to 60) and carries no priority.
Downstream messages arrive on the control ring, which takes the frames of
internal priority 7: the OMCI messages, and any other frame the switch is set to
give priority 7. A flood of data to the CPU therefore does not drop them (see
"The rings" and "Sizes, load and locking"). The four bytes that
follow each downstream message, and the flow, T-CONT and Port-ID of the OMCC,
belong to the PON MAC
(Documentation/networking/device_drivers/pon/rtl9602c.rst); the OMCI port
itself is part of the PON class (Documentation/networking/pon.rst).

Statistics
==========

The conduit counts in the ``net_device`` statistics that ``ip -s link show cpu``
prints. It has no ``ethtool`` statistics of its own: ``ethtool -S cpu`` lists
the switch's counters for the CPU port, which DSA adds under the prefix
``s00_p03_`` (Documentation/networking/dsa/rtl9602c.rst). The switch counts the
same frames on its side of the engine, so its counters cross-check the
conduit's: the frames the switch delivered to the CPU port match the frames the
conduit received plus the missed frames, to within a few (see "Registers"), and
``tx_packets`` of the conduit tracks the switch's CPU-port counter (see "Sizes,
load and locking"). The two sides are read with::

    ip -s link show cpu
    ethtool -S cpu

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Counter
     - Counted
   * - ``rx_packets``
     - For each frame handed to the stack, and for each frame that the OMCI
       handler or the data-frame handler took.
   * - ``rx_bytes``
     - For each frame handed to the stack, its length with the Ethernet header,
       taken before ``eth_type_trans()`` pulls it; for each frame or message
       that a handler took, its length as handed over.
   * - ``rx_dropped``
     - A frame for which no replacement buffer could be allocated or mapped. The
       frame is dropped and its own buffer goes back to the descriptor.
   * - ``rx_errors``
     - A descriptor with ``RTL9602C_NIC_RXD_FCS_ERR`` or
       ``RTL9602C_NIC_RXD_DMA_ERR`` set.
   * - ``rx_crc_errors``
     - Those with ``RTL9602C_NIC_RXD_FCS_ERR`` set.
   * - ``rx_fifo_errors``
     - Those with ``RTL9602C_NIC_RXD_DMA_ERR`` set.
   * - ``rx_length_errors``
     - A frame in one descriptor shorter than 20 bytes or longer than 1536 by
       the length in word 0; a frame in pieces longer than its buffer or cut
       short, and a piece without its first.
   * - ``rx_missed_errors``
     - Frames the engine dropped for want of a receive descriptor: on every
       poll the 16-bit difference of ``RTL9602C_NIC_RX_NO_DESC_CNT`` since the
       previous poll.
   * - ``tx_packets``, ``tx_bytes``
     - When the reaper finds a completed descriptor that carries a frame: a
       data frame or an OMCI message, not the transmit test. The bytes are the
       frame's length, padding included, without the FCS.
   * - ``tx_dropped``
     - A data frame that could not be padded or mapped, or that is longer than
       ``RTL9602C_NIC_TX_MAX``. The tag driver also
       counts here the frames it drops on the ``pon`` interface, in that
       interface's statistics.

The frames the switch sent up are also counted per trap reason, in memory, for
frames that carry a CPU tag, that the OMCI handler did not take, while DSA uses
the conduit. ``/sys/kernel/debug/rtl9602c-eth/rxreason`` (mode ``0600``) lists

clears all the counts::

    reason   0  1542
    reason  16  87

Before any tagged frame has arrived it reads "no tagged frame has been
received".

Sequences
=========

The steps are in the order the driver takes them. The tag in parentheses at the
end of a step is the tag of the fact the step rests on (see the tables above);
a step tagged I rests on an assumption.

Probe
-----

1. Map the register window. Purpose: reach the engine. (M)
2. Stop the engine, before anything is allocated: read ``RTL9602C_NIC_DMA_CTRL``,
   ``RTL9602C_NIC_IRQ_STAT`` and the four ring registers; write 0 to
   ``RTL9602C_NIC_IRQ_MASK``; halt the engine as at stop (0 to
   ``RTL9602C_NIC_DMA_CTRL``, then 0 to ``RTL9602C_NIC_RING_CFG``); read
   ``RTL9602C_NIC_DMA_CTRL`` back; wait 1 to 2 ms; write ``0xffff`` to
   ``RTL9602C_NIC_IRQ_STAT``; log the registers as found and the control
   register after the stop. Purpose: whatever ran before the kernel may have
   used the engine and left it enabled, with rings of its own in memory that the
   kernel now owns; the engine is stopped and its status clear before the
   kernel's own rings are written, which the halt of a stop is known to make it
   take (the transmit test at open passes after one). (T for the stop, I that it
   stops every state the engine can be left in)
3. Allocate the network device with ``RTL9602C_SW_PORTS`` (4) transmit queues
   and one receive queue, name it ``cpu`` and keep dsts (``netif_keep_dst()``).
   Purpose: a queue per switch port carries the destination port, the name
   makes the user ports ``sfp@cpu`` and ``pon@cpu``, and the flow of a GEM
   frame travels in a dst. (M, T)
4. Take the interrupt from the device tree, and allocate the arrays that hold
   each receive descriptor's buffer, per ring. Purpose: reach the engine's
   interrupt line. (M)
5. Read the MAC address from the engine's address registers. Use it if it is a
   valid unicast address; otherwise warn and use a random one. Purpose: the
   interface has the unit's own address. (M)
6. Allocate one ``METADATA_HW_PORT_MUX`` dst per switch port, with ``port_id``
   the port number, and have the device free them, at a failed probe and at its
   removal. Purpose: a received frame gets the dst of its source port. (T)
7. Add the NAPI poll, and create the debugfs directory ``rtl9602c-eth`` with
   its files ``rxreason`` and ``rings``. Purpose: the poll does the receive
   work, and the reasons and the rings can be read back. (M)
8. Register the network device and log the address line. Purpose: DSA attaches
   the user ports to a registered conduit. (T)
9. Run the transmit test on rings set up for it alone and free them again; log
   the result. The result does not stop the probe. Purpose: report whether the
   engine takes and returns a descriptor. (M)

Setting the engine up
---------------------

This is done by the open, and by the transmit test at probe, in this order:

1. Allocate the three rings and give every receive descriptor a mapped buffer:
   ``RTL9602C_NIC_DESC_OWN | 0x600``, and ``RTL9602C_NIC_DESC_RING_END`` on the
   last of each ring. Purpose: the engine may fill any descriptor once it is
   started. (T)
2. Write the transmit ring's bus address to ``RTL9602C_NIC_TX_RING_BASE`` and 0
   to ``RTL9602C_NIC_TX_RING_CUR``; the same for the data ring. Purpose: both
   sides start at descriptor 0. (M)
3. Write ``0x0f`` to ``RTL9602C_NIC_RX_FILTER``, ``0x0c00`` to
   ``RTL9602C_NIC_TX_CFG`` and ``0x0a`` to ``RTL9602C_NIC_CTRL``. Purpose:
   accept every frame the switch hands over, and a receive format that does not
   depend on the boot loader. (T)
4. Write 255 to ``RTL9602C_NIC_RX_RING_LEN`` and to
   ``RTL9602C_NIC_RX_RING_TAIL``. Purpose: a 256-descriptor ring, all of it
   available. (T)
5. Write 16 to ``RTL9602C_NIC_RX_PAUSE_ON_THR`` and 48 to
   ``RTL9602C_NIC_RX_PAUSE_OFF_THR``; then write 0 to
   ``RTL9602C_NIC_RX_RING_LEN_HI``, ``RTL9602C_NIC_RX_RING_TAIL_HI`` and
   ``RTL9602C_NIC_RX_PAUSE_OFF_THR_HI``. Purpose: the thresholds, and no high
   part left over from the boot loader. (M for the thresholds, T for the high
   parts)
6. Write the control ring's bus address to ``RTL9602C_NIC_RX2_RING_BASE`` and
   31 to ``RTL9602C_NIC_RX2_RING_LEN``; read ``RTL9602C_NIC_RX2_RING_CUR`` and,
   if it is inside the ring, begin there and choose ``0x20000000`` for the
   steering, otherwise warn and choose 0; write the index before it to
   ``RTL9602C_NIC_RX2_RING_TAIL`` and ``0x00020006`` to
   ``RTL9602C_NIC_RX2_PAUSE_THR``. Purpose: a 32-descriptor control ring, all
   of it available, from the index the engine keeps. (M; I for the
   thresholds)
7. Write 0 to ``RTL9602C_NIC_REG_13FC``. Purpose: a known value in a register
   whose function is not established. (I)
8. Write all ones to ``RTL9602C_NIC_MC_HASH_LO`` and
   ``RTL9602C_NIC_MC_HASH_HI``. Purpose: no multicast group is filtered. (T)
9. Write ``0x20000000`` to ``RTL9602C_NIC_CFG``, and the steering chosen in
   step 6 to ``RTL9602C_NIC_RX_PRI_TO_RING``. Purpose: the receive interrupt
   of both rings stays in ``RTL9602C_NIC_IRQ_STAT``, and priority 7 goes to the
   control ring. (M)
10. Clear bits 7 and 6 of ``RTL9602C_NIC_MEDIA_STAT``, keeping the other
    bits. Purpose: no pause between the engine and the switch. (M)
11. Write ``0x901eff04`` to ``RTL9602C_NIC_CPUTAG`` and ``0x4072`` to
    ``RTL9602C_NIC_CPUTAG_SRC``. Purpose: the CPU tag in the descriptors, both
    directions. (T for the tag register, M for the source register)
12. Write ``0x32000001`` to ``RTL9602C_NIC_RING_CFG``, then ``0xc059f130`` to
    ``RTL9602C_NIC_DMA_CTRL``. Purpose: configure, then start. (T)

Open
----

1. Allocate the rings and set the engine up (above). Purpose: descriptors and
   registers are ready before anything can arrive. (T)
2. Read ``RTL9602C_NIC_RX_NO_DESC_CNT`` as the base for the missed frames.
   Purpose: the count starts from the value at open. (M)
3. Run the transmit test. Its result is logged and does not stop the open.
   Purpose: every boot shows whether the engine takes and returns a
   descriptor. (M)
4. Enable the poll. Purpose: the poll can run as soon as the interrupt does.
   (T)
5. Write ``0xffff`` to ``RTL9602C_NIC_IRQ_STAT``. Purpose: nothing stale
   reaches the handler. (T)
6. Request the interrupt; if that fails, undo the steps above and fail the
   open. Purpose: the handler is installed before any cause is unmasked. (M)
7. Write ``RTL9602C_NIC_IRQ_MASK_RXTX`` to ``RTL9602C_NIC_IRQ_MASK``. Purpose:
   from here the causes in the mask raise the interrupt. (T)
8. Start the transmit queues and log the open line. Purpose: the stack may
   transmit. (T)

The transmit test
-----------------

The test sends one 60-byte broadcast frame from the interface's own address,
aimed at the SerDes port (word 2 ``RTL9602C_NIC_TXD_CPUTAG_EN |
RTL9602C_NIC_TXD_PRI_EN``, word 3 ``RTL9602C_NIC_TXD_DST_SFP |
RTL9602C_NIC_TXD_L34_BYPASS``), kicks the engine, and waits up to 100 times,
100 to 200 microseconds each, for OWN to clear. The kernel of this board has
no timer finer than its 4 ms tick, so each wait lasts a tick and the test gives
up after 400 ms. On success both driver indices step past the descriptor it
used, because the engine has moved past it (see "The ring registers"). Either
way the descriptor is taken back and its buffer freed.

   * - Fact
     - Tag

   * - At open the transmit test passes on every boot.
     - M
     - The open line of every boot: ``transmit test ok``.
   * - At probe, before the probe stopped the engine first, the same test (rings

Transmitting a data frame
-------------------------

1. Pad the frame to 60 bytes and map it for DMA. Purpose: with the appended FCS
   the frame meets the 64-byte minimum, and the engine reads it from memory.
   (P)
2. Build word 0: ``RTL9602C_NIC_DESC_OWN``, first and last segment,
   ``RTL9602C_NIC_TXD_ADD_FCS``, ``RTL9602C_NIC_TXD_NO_REWRITE`` and the length;
   add ``RTL9602C_NIC_TXD_FLOW_SEL`` and take the flow from the dst if the frame
   carries a flow dst. Purpose: describe the frame to the engine. (T)
3. Take the ring lock. If the ring is full, stop every queue, drop the lock,
   unmap the frame and return busy. Purpose: one ring and one lock serve every
   queue, and the stack retries when the ring has room again. (T)
4. Write word 1 (the buffer), word 2 (``RTL9602C_NIC_TXD_CPUTAG_EN |
   RTL9602C_NIC_TXD_PRI_EN`` and the priority), word 3 (the queue's port, the
   flow, ``RTL9602C_NIC_TXD_L34_BYPASS``) and word 4 (0). Purpose: aim the frame
   at one port, with its priority and flow. (T)
5. Write word 0 last, with ``RTL9602C_NIC_DESC_RING_END`` if this is the last
   descriptor of the ring. Advance the head, and stop the queues if the ring is
   now full. Purpose: the engine must not take the descriptor before its other
   words are in memory. (T)
6. Kick: ``wmb()``, read ``RTL9602C_NIC_DMA_CTRL``, then write
   ``RTL9602C_NIC_DMA_CTRL_INIT | RTL9602C_NIC_DMA_CTRL_TX_POLL``. Drop the
   lock. Purpose: tell the engine the ring has work. (T, and I for the read)

Receiving
---------

For each descriptor of a ring, up to the budget the poll gives it:

1. Stop at the first descriptor with OWN set. Purpose: the engine has not
   filled it yet. (T)
2. ``dma_rmb()``; read words 2 and 3. Purpose: they are this frame's. (T)
3. Drop and count a frame with an error bit set or with a bad length. Purpose:
   such a frame never reaches the stack, and its buffer returns to the
   descriptor. (I for the error bits, T for the lengths)
4. Get a replacement buffer first; if there is none, drop the frame and keep its
   buffer for the descriptor. Purpose: the ring never holds a descriptor without
   a buffer. (M)
5. Skip the 2-byte offset and remove the FCS by length. Purpose: the frame
   starts at its first byte. (T)
6. Offer a frame marked OMCI to the OMCI handler; if it takes the frame, go to
   step 10. Purpose: OMCI messages go to the OMCI port. (T)
7. For a tagged frame while DSA uses the conduit: count its trap reason, offer
   it to the data-frame handler, and if that leaves it attach the dst of its
   source port. Purpose: the frame reaches its GEM interface or its user port.
   (M, T)
8. Take off a PTP timestamp tag if the frame carries one. Purpose: the frame
   reaches the stack as it was sent, with its hardware timestamp. (M)
9. Hand the frame up with ``eth_type_trans()`` and ``netif_receive_skb()``.
10. Give the descriptor back, with the new buffer or the old one, and write its
    index to the ring's tail, ``RTL9602C_NIC_RX_RING_TAIL`` or
    ``RTL9602C_NIC_RX2_RING_TAIL``. Purpose: without the write the ring runs
    dry. (T)

The interrupt and the poll
--------------------------

The interrupt:

1. Read ``RTL9602C_NIC_IRQ_STAT``. If it is zero the interrupt is not the
   engine's. Purpose: tell an interrupt of the engine from one that is not.
   (T)
2. Write the value back. Purpose: acknowledge every cause that was pending.
   (T)
3. If the poll is not already scheduled, write 0 to ``RTL9602C_NIC_IRQ_MASK``
   and schedule it. Purpose: the poll does the work with the causes masked. (T)

The poll:

1. Fold in the missed frames (``RTL9602C_NIC_RX_NO_DESC_CNT``). Purpose: the
   16-bit counter wraps quickly under load. (M)
2. Reap the transmit completions. Purpose: free the sent frames and wake the
   queues. (T)
3. Receive (above) from the control ring, up to the budget, then from the data
   ring with what is left of it. Purpose: a full budget of data cannot hold an
   OMCI message back. (M)
4. If it finished under the budget, complete the poll and write
   ``RTL9602C_NIC_IRQ_MASK_RXTX`` to ``RTL9602C_NIC_IRQ_MASK``. Purpose: let the
   causes raise the interrupt again. (T)

Stop
----

1. Log the totals, then stop the transmit queues. Purpose: nothing new is
   posted. (T)
2. Write 0 to ``RTL9602C_NIC_IRQ_MASK``, free the interrupt and stop the poll.
   Purpose: nothing runs against the rings once the engine is halted. (T)
3. Write 0 to ``RTL9602C_NIC_DMA_CTRL``, then 0 to ``RTL9602C_NIC_RING_CFG``.
   Purpose: halt the engine. (T)
4. Reap what the engine sent, then free the rings and their buffers. Purpose:
   nothing is left mapped. (T)

Known limitations
=================

- The conduit takes a frame longer than 16 bytes with EtherType ``0x8899`` at
  offset 12 and the protocol byte 4 at offset 14 to carry a PTP timestamp tag,
  as every tag seen on this board did. A tag with another protocol byte would
  go up as an ordinary frame, unstamped.
- The transmit test at probe is meant to pass in every start. Before the probe
  stopped the engine first, it failed when the boot loader had just used the
  engine to receive an image, although the engine transmitted and the same test
  at open passed (see "The transmit test"). The result is only logged. That the
  stop covers every state the engine can be left in is not verified (see "Open
  questions").
- The engine drops frames when it has no receive descriptor free. The CPU's
  receive ceiling is about 24,000 to 25,000 frames/s whatever the frame size,
  and beyond it the excess is counted in ``rx_missed_errors``. The receive
  pause thresholds have no effect, because the switch's side of the pause is
  not enabled. OMCI messages have the control ring to themselves only while
  nothing else is given internal priority 7: a frame the switch is set to give
  priority 7 on its way to the CPU, through its priority selection (``dcb
  apptrust`` with the PCP or DSCP maps, or a port's default priority), shares
  the control ring with them.
- The largest MTU is 1508, room for PPPoE's 1500-byte packets. In its default
  mode the transmit engine stops on long frames, and its jumbo mode, which
  sends them, is not used (see "Transmit"), so jumbo frames are not offered.
  DSA limits the largest MTU of the user ports by the conduit's, so a larger
  MTU on a user port fails with ``-ERANGE``. The limit that the switch itself
  applies is described in Documentation/networking/dsa/rtl9602c.rst.
- A frame marked as OMCI that no handler takes is dropped and counted in
  ``rx_dropped``: when no OMCI handler is attached, when the frame carries no
  CPU tag, and when the handler declines it (the switch driver's handler
  declines a frame from any port but the PON port). Such a frame has no
  Ethernet header to go up the ordinary receive path with.

Open questions
==============

These are the facts tagged **I** in the tables above, each with what would
settle it. The first list holds the assumption the driver depends on: the
driver is correct on this board only if it holds. The second list holds the
questions to which the code is indifferent: it works whichever way they
resolve. Four of them are still worth a board test, because they decide what
the switch needs in the CPU tag; they come first.
